## 13.1 SRE核心运维理念：指标驱动、自动化驱动、容错优先、风险前置

### 生产问题

扩容凭经验、稳定性凭感觉、风险凭记忆——资深工程师在时一切正常，其离职后体系崩坏。**运维能力不完成从"个人经验"到"SRE 方法论"的升级，就无法沉淀、无法扩展、无法自治**。

### 传统方案失效原因

经验不可复现、手工不可扩展、救火不建容错、风险被动等真实故障暴露——定论，不再论证。失效根因：没有用四大理念（指标/自动化/容错/风险前置）重塑运维。

### 架构约束与权衡

四大核心理念各一句（定论）+ 落地承接：

| 理念 | 一句话 | 落地承接 |
|---|---|---|
| **指标驱动** | 扩容/稳定性/成本决策必须引用指标数字，拒绝"感觉还行" | 11 章观测、12.2 SLO、13.2/13.3 |
| **自动化驱动** | 能自动不人工——调谐、交付、弹性、回退全部声明式 | 第 5、9、15 章 |
| **容错优先** | 设计先假设必失败：探针/反亲和/PDB/超时降级先于"不出错" | 第 5、6、7 章 |
| **风险前置** | 韧性靠主动注入验证，不等真实故障来考试 | 12.5 混沌 |

权衡：方法论建设的前期投入，换来的是**组织级能力而非个人能力**——这是 SRE 用工程化替代经验化的唯一代价。

### 最小可行方案

1. **指标驱动**：决策必引指标（SLO 达成率/容量水位/成本趋势），取不到数字的议题不决策。
2. **自动化驱动**：能自动（调谐/交付/弹性/回退）不人工。
3. **容错优先**：探针（5 章）、反亲和（6 章）、超时降级（7 章）、PDB（5 章）成为交付标配。
4. **风险前置**：每月一次极简混沌注入（12.5）。

### 生产落地实现

四大理念的最小落地制品——**SRE 周会决策卡**：任何扩容/稳定性/成本议题，开场先取三个数：

```bash
# 决策卡取数（VictoriaMetrics，11 章栈；endpoint 以实际部署为准）
# ① SLO 达成率（12.2 口径）：< 99.9% → 稳定性议题优先
curl -sG 'http://vmsingle-vmstack.observability.svc:8428/api/v1/query' \
  --data-urlencode 'query=1 - sum(rate(http_requests_total{job="api",code=~"5.."}[30d])) / sum(rate(http_requests_total{job="api"}[30d]))'
# ② 容量峰值水位（13.2）：≥70% → 扩容议题上会
# ③ 成本月环比（13.3 账单拆分）：>±10% → 成本议题上会
```

- 云服务映射：四大理念在托管底座上的开箱承接是 **ACK 节点池自动修复/自动升级（对照 EKS 托管节点组，4.2）**——"容错优先 + 自动化驱动"由云厂商机制兜底；指标取数跑在自建 VM 栈（11 章）。
- 数字基准：SLO 99.9% = 月错误预算 43.2 分钟（12.2）；容量峰值水位红线 70%（13.2）；成本环比告警线 ±10%（13.3）。

### 典型故障案例

某团队扩容全凭资深工程师"手感"，常扩过头（浪费）或扩不够（故障）。改为决策卡制度（水位超线才扩、扩多少按 13.2 公式链算）后，既不浪费也不欠。

点评：**指标驱动把"运维艺术"变成"运维工程"**，决策可复现、可审计。

### 根因定位

拆到底是**运维靠个人经验而非方法论**——经验随人流失，方法论沉淀为组织资产。

### 长效治理方案

- 四大理念成为团队决策共识，决策卡进周会制度。
- 决策必引指标、能自动不人工、设计假设失败、韧性主动验证。

### 自动化/自治闭环

四大理念是三层自治的方法论底座：L1 自动化+容错、L2 指标驱动、L3 自动化极致，都从这里出发——本节是全书自治体系的"理念第 0 层"。

### 生产检查清单

- [ ] 运维决策是否指标驱动（决策卡三数：SLO/水位/成本环比）？
- [ ] 是否能自动不人工（自动化优先）？
- [ ] 设计是否容错优先（探针/反亲和/PDB/降级成交付标配）？
- [ ] 是否每月主动验证韧性（12.5 极简注入）？
- [ ] 运维能力是否沉淀为方法论（非依赖个人）？

## 13.2 业务容量预估、弹性治理、峰值资源保障常态化机制
<!-- 成本对象=云账单：容量算例落在 ACK ECS 节点池（16C64G 为主规格，对照 EKS 托管节点组）。公式链每步可复算；弹性只接 HPA（6.5）/KEDA（15.3）既有制品，不重复展开。 -->

### 生产问题

为峰值常备 3 倍资源，平时节点 CPU 利用率不到 20%——每月照付 3 倍节点账单；真到大促，手动扩容又跟不上，一次雪崩赔掉全年省下的钱。**容量无预估、弹性无策略、峰值无保障，要么浪费要么故障**。

### 传统方案失效原因

- 无容量预估：不知业务增长需要多少资源，被动应对。
- 弹性被动：出事才手动扩，滞后且易错；平时常备过量，闲置烧钱。
- 峰值无保障：峰值来时资源不够，请求排队雪崩。

失效根因：容量没有"预估 + 弹性 + 保障"的常态化机制。

### 架构约束与权衡

容量治理三机制：

| 机制 | 含义 | 权衡 |
|---|---|---|
| **容量预估** | 压测定单副本容量，公式链算副本/节点 | 预估精度 vs 投入 |
| **弹性治理** | HPA（6.5）/KEDA（15.3）按指标自动扩缩 | 弹性灵敏度 vs 稳定性 |
| **峰值保障** | 已知峰值提前预留，突发峰值节点池快速扩容 | 成本 vs 可用性 |

权衡的核心：**容量治理平衡"平时不浪费"与"峰值够用"**——靠压测定容 + 公式链 + 自动弹性，而非常备过量。

### 最小可行方案

1. **定容**：压测得出单副本容量，公式链算出副本数与节点数（每步可复算）。
2. **弹性**：CPU 密集 HPA（6.5），业务瓶颈 KEDA（15.3）；maxReplicas = 公式链峰值副本。
3. **保障**：已知峰值（大促）提前扩节点池；突发峰值靠节点池弹性快速加节点 + 弹性上限防过扩。
4. **常态化**：月度容量评审表，峰值水位 ≥70% 当月必须出结论。

### 生产落地实现

**① 容量公式链与可复算算例**（每步代入即得，输入→副本→节点→成本）：

```text
输入：峰值 QPS 2,000（历史 P99 1,550 × 1.3 增速 ≈ 2,000，取整）
      单副本容量 250 QPS（压测实测，见②）

副本层：
  基准副本数 = ceil(2,000 ÷ 250)            = 8
  冗余副本数 = ceil(8 × 1.3)                = 11    ← 1.3 = 冗余系数（可调: 1.2–1.5）
  多 AZ 对齐 = 向上取 3 AZ 整数倍（6.3）    = 12    ← 3 AZ × 4 副本；挂 1 个 AZ 仍剩 8 副本
节点层（16C64G ECS 节点，Pod request 1.5C/4G）：
  每节点 Pod 数 = floor(16C × 80% ÷ 1.5C)   = 8     ← 80% 为 DaemonSet/系统组件预留（可调: 75–85%）
  节点数 = ceil(12 ÷ 8) = 2，加 N+1 冗余    = 3     ← 3 AZ 各 1 台，节点池下限
自检：挂 1 台节点/AZ → 剩 8 副本 = 基准副本数 ✓（0.8 压测安全系数仍在兜底）
成本：16C64G 按量 ≈¥3.4/时（×720h ≈¥2,450），包月常见 6–7 折 ≈¥1,700–2,100/月 → 取 ¥1,800：3 × ¥1,800 ≈ ¥5,400/月（量级示例，以官网当期价为准）
```

冗余系数 1.3 不是拍出来的常数——取 1.2 还是 1.5，取决于三个变量（可调区间 1.2–1.5 的取值依据）：

| 决策变量 | 偏向 1.2（低冗余） | 偏向 1.5（高冗余） |
|---|---|---|
| 流量波动性 | 平稳可预测（内部系统/工作日周期） | 突发频繁（大促/秒杀/投放拉新） |
| 扩容链路时延 | 秒级（镜像已缓存、节点池有余量） | 分钟级（节点池扩容 + 有状态加载） |
| 成本敏感度 | 成本红线紧，信任弹性兜底（HPA/KEDA） | 稳定优先，愿意为冗余付"保费" |

**② 压测定容**（单副本容量是整条公式链的地基，必须实测不许拍）：

```bash
# 步骤：副本钉死 1（先关 HPA/KEDA）→ 阶梯加压 200/250/300/350 QPS → 找 p99 越限点 → 打 0.8 安全系数
kubectl -n prod scale deploy/demo-api --replicas=1

# vegeta：速率精确阶梯（每档 2 分钟）
echo "GET http://9.0.4.12:8080/api/orders" | vegeta attack -rate 250/s -duration 2m | vegeta report

# wrk 等价（并发压力型）：8 线程 × 500 并发 × 2 分钟
wrk -t8 -c500 -d120s --latency http://9.0.4.12:8080/api/orders

# 判定门槛：p99 ≤ 500ms（12.2 SLO 口径）且 5xx < 0.1%
# 实测：310 QPS 时 p99 开始越限 → 单副本容量 = 310 × 0.8 ≈ 250 QPS（安全系数可调: 0.7–0.85）
```

**③ 月度容量评审表**（每月一次；当前水位 = 30 天均值/容量，峰值水位 = 30 天峰值/容量）：

| 服务 | 单副本容量 | 当前副本 | 部署容量 | 实际峰值 | 峰值水位 | N+1 达标（<70%） | 结论 |
|---|---|---|---|---|---|---|---|
| demo-api | 250 QPS | 12 | 3,000 | 2,000 | 67% | ✓ | 持平观察 |
| pay-svc | 200 QPS | 6 | 1,200 | 950 | 79% | ✗ | 扩到 9 副本（3 AZ × 3），KEDA 上限同步上调（15.3） |
| report-svc | 120 QPS | 9 | 1,080 | 150 | 14% | ✓ | 缩到 3 副本（AZ 整数倍），释放配额接 13.3 规格账 |
| 集群（节点） | 8 Pod/节点 | 3 节点 | 24 槽位 | 17 | 71% | ✗ | +1 节点，下月复查 |

红线：**峰值水位 ≥70% = N+1 失守预警（挂一台后扛不住峰值），当月必须出扩/缩结论**；水位 <30% 连续两月 → 缩容。数字体感：70% = 留给大促的缓冲还剩三成——demo-api 当前 67%，再叠一波三成涨幅的正常大促流量就顶满，扩容必须发生在红线之前而非之后。水位超线自动告警（vmalert，11 章栈）：

```yaml
groups:
- name: capacity
  rules:
  - alert: PeakWaterLevelHigh           # 峰值水位 ≥70%：N+1 失守预警（13.2 评审红线）
    expr: sum(rate(http_requests_total{job="api"}[5m])) / (250 * 12) > 0.70
    for: 10m                            # 降噪: 持续 10 分钟才算真峰值（12.1）
    labels: {severity: P3}
    annotations:
      action: "进月度容量评审，公式链重算副本/节点，当月出结论"
```

瞬时巡检用 kubectl top（30 天峰值/均值走 11 章指标出报表）：

```bash
kubectl top nodes --sort-by=cpu | head -5        # 节点当前水位
kubectl top pods -A --sort-by=cpu | head -10     # 吃 CPU 大户（缩容/规格优化线索，接 13.3）
```

**④ 峰值保障两件套**（已知峰值与突发峰值分治）：

- 已知峰值（大促/活动）：提前 3 天把节点池期望容量扩到公式链峰值档（如 3 → 6 节点），活动后回调；保底节点用包月，增量节点走抢占式实例（13.3，省 50%+）。
- 突发峰值：ACK 节点池弹性（4.2）+ Cluster Autoscaler 快速加节点；HPA/KEDA 的 maxReplicas = 公式链峰值副本，防过扩打爆节点池与团队配额（6.4）。

云服务映射：容量落点是 **ACK ECS 节点池（多 AZ + 自动伸缩，对照 EKS 托管节点组）**，峰值增量节点优先抢占式实例（阿里云 Spot，对照 AWS Spot，13.3 详述）。数字：本算例集群 3 节点起步 ≈ ¥5,400/月（包月，① 口径）；大促一周翻倍到 6 节点，增量 3 节点 × 168h × ¥1.8/时（Spot，≈按量 ¥3.4/时的 5 折）≈ ¥900（量级示例，以官网当期价为准）。

### 典型故障案例

某大促前团队为省成本把副本压到 4（峰值水位 90%+），峰值来时手动扩容、节点不够 Pod 大量 Pending，排队 8 分钟后雪崩。建机制后：公式链定 12 副本常态水位 67%，KEDA 按请求速率自动扩（15.3），节点池提前 3 天扩到 6 台——次年大促平稳通过，且平时不多付一台节点的钱。

点评：**容量治理是"平时省"与"峰值扛"的平衡**，靠定容 + 弹性而非常备。

### 根因定位

先给结论：容量事故的根因从来不是"资源不够"，而是**无定容方法（多少才够没人算得出）+ 无常态化水位观测（快不够了没人知道）**。

### 长效治理方案

- 每服务有压测定容记录，公式链重算进月度评审。
- 峰值水位 70% 红线告警常开，超线当月出结论。
- 弹性分层（HPA/KEDA 各管一类负载），上限锚定公式链峰值副本。
- 已知峰值提前扩池、突发峰值节点池弹性，配 PDB 保护（6.3）。

### 自动化/自治闭环

容量治理是 L2 运维自治（15 章）的弹性战场：容量预估提供自治的"预判"，HPA/KEDA 提供"执行"，峰值水位红线提供"边界"——本节是 L2 自动处置在资源层的数据与边界输入。

### 生产检查清单

- [ ] 每个核心服务有压测定容记录（单副本容量 + 安全系数）？
- [ ] 副本/节点由公式链算出且多 AZ 整数倍（6.3）？
- [ ] 峰值水位 <70% 红线告警常开、月度评审出表？
- [ ] 弹性按负载特性分层（HPA/KEDA），上限 = 公式链峰值副本？
- [ ] 已知峰值提前扩池、突发峰值有节点池弹性 + PDB 护栏？

## 13.3 FinOps极简落地模型：资源利用率评估、闲置回收、规格优化、成本分摊与业务对齐（不展开FinOps平台与复杂体系）
<!-- 成本对象=云账单（ACK 控制面/ECS 节点/云盘/SLB/流量/备份）+ 自建平台组件（VM/Loki/Tempo 所在 VM/盘，11 章）。极简四环节，不做平台，本节只管集群整体成本框架。 -->

### 生产问题

成本失控的第一反应是"砍预算"，但真黑洞藏在账单明细里：PVC 早删了、云盘却空挂 18 个月照常扣费；负载申请 16 核实际用 1 核；月底一张总账单，没人说得清哪个团队花了多少。**成本不可见、不可归因、不可优化——FinOps 无落地，预算黑洞持续吞噬**。

### 传统方案失效原因

- 不评估利用率：闲置与超配不可见（11 章指标有了没人看）。
- 不回收闲置：删掉的负载留下僵尸 PV/云盘，长期扣费。
- 规格不优化：request 申请即固定，永不回调。
- 不分摊：一张总账单，成本无法对齐业务。

失效根因：没有"利用率评估 → 闲置回收 → 规格优化 → 成本分摊"的极简闭环（FinOps 平台归 V2，不做）。

### 架构约束与权衡

四环节极简模型（成本对象两层：云账单 + 自建平台组件）：

| 环节 | 极简实践 | 权衡 |
|---|---|---|
| **利用率评估** | 月账单拆分 + VM 指标水位（11 章） | 评估成本 vs 收益 |
| **闲置回收** | 巡检表定期识别回收（PV/负载/节点/高配池） | 回收 vs 误删风险 |
| **规格优化** | 按实际用量调 request/limit（6.4 兜底） | 规格 vs 弹性 |
| **成本分摊** | 云标签 + namespace 映射到业务 | 精度 vs 简单 |

权衡的核心：**极简四环节让成本可见、可归因、可优化**，不依赖重型 FinOps 平台。

### 最小可行方案

1. **利用率评估**：每月出账单拆分表，环比 >±10% 的项必须写解释。
2. **闲置回收**：巡检表周期跑命令，僵尸资源先进工单再回收。
3. **规格优化**：超配检测规则出缩规格清单，LimitRange 兜底（6.4）。
4. **成本分摊**：team/env/cost-center 三标签 + namespace 映射，月报出"每团队成本"。

### 生产落地实现

**① 月账单拆分**（10 节点生产集群量级示例，价格以官网当期价为准）：

| 账单项 | 明细 | 月成本（量级示例） | 占比 |
|---|---|---|---|
| ECS 节点 | 10 × 16C64G 包月为主（含部分 Spot，13.2① 口径） | ¥18,000 | 62% |
| 云盘 | 系统盘 + ~20 块 ESSD 数据盘 | ¥3,600 | 12% |

**② 抢占式实例（Spot）：节点成本的最大杠杆**（节点占账单 60–70%，Spot 是其中最重的一根杠杆）：

| 负载类型 | 上 Spot | 条件与说明 |
|---|---|---|
| 无状态在线服务 | ✓ | 多副本 + PDB + topologySpread 打散（6.3），中断=驱逐重建，秒级 |
| 批处理/CI/离线计算 | ✓✓ | 天然可重算，断了重跑；配断点续跑更稳 |
| 长连接网关 | ⚠️ 慎用 | 连接排水要时间，中断代价=活跃连接掉线；要用必须混部常规节点池 + KEDA 快速补副本兜底（15.3） |
| 有状态数据库 | ✗ | 云盘 AZ 绑定 + 重建代价高，不省这个钱 |

思想实验——"省出来的利润，一次回收赔光"（先自己猜答案，再往下读）：

> 墨丘里商城团队发现 im-gateway 的长连接流量夜间只有白天的 10%，于是把夜间副本全部切到 Spot 节点，当月账单省了 60%。先猜：三个月内一定会发生什么？

揭晓：某晚云厂商库存收紧，批量回收 Spot 节点——长连接排水要 3–5 分钟/副本，通知窗口内排不完；KEDA 拉起的新副本又撞上节点供给不足，Pod 大量 Pending，夜间 SLA 跌穿。**省下的钱不够赔一次 SLO 违约与客诉**。Spot 的承诺从来不是"不被回收"，是"回收前尽力通知你"——通知窗口（约 2–5 分钟）跑不过排水与重建时长（3–5 分钟）的负载，天然不适合无预热的 Spot，这正是上表"长连接网关 ⚠️ 慎用"背后的机制。

把这笔账写成契约——**Spot 保证等级表**（你到底买到了什么）：

| 保证维度 | 承诺 | 不承诺 |
|---|---|---|
| **生命周期** | —— | 节点存活时长：随时可能被回收，与你的发布/大促节奏无关 |
| **回收通知** | 回收前尽力通知（元数据/系统事件，分钟级） | 通知窗口大于你的恢复时长——窗口仅 2–5 分钟，排不完水就是硬中断 |
| **价格** | 大幅低于按量（1–5 折，见下） | 折扣恒定：随供需波动，高峰期可能收紧 |
| **库存供给** | —— | 供给充足：高峰期/热门规格可能抢不到，弹性拉起的新副本同样 Pending |

适用判断就一条赛跑：**通知窗口 vs 恢复时长**——赢得起（无状态秒级重建、批处理可断点重跑）放心上；跑不赢（长连接分钟级排水、有状态库）别省这个钱。

价格事实：阿里云抢占式实例常见折扣至按量价的 50%–90% off（即 1–5 折，随供需波动，以官网当期价为准）；AWS Spot 同量级。算例：4 台无状态节点从按量 ¥3.4/时（4 × 720h ≈ ¥9,800/月）切 Spot ¥1.8/时（≈按量 5 折，≈¥5,200/月）：月省 **≈¥4,600，约省总账单 15%**。

中断通知语义：阿里云 Spot 释放前约 5 分钟发出系统事件/元数据可查（以官方文档为准）；AWS Spot 提前 2 分钟通知（EventBridge 事件 + IMDS 元数据）。排水必须在中断窗口内完成。生产优先托管路径——ACK 节点池对被释放节点的自动替换 + 云事件驱动 drain（AWS 用 aws-node-termination-handler 或 Karpenter 中断处理）；自研 DaemonSet 监听是兜底：

```bash
# Spot 中断监听（DaemonSet 思路：每个 Spot 节点跑一份监听容器，RBAC 允许 cordon/drain）
while true; do
  # 阿里云 ECS 元数据（返回空=未通知；以官方文档为准）
  T=$(curl -s -m 2 http://100.100.100.200/latest/meta-data/instance/spot/termination-time)
  # AWS 对照（IMDSv2）：
  # TOK=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 60")
  # T=$(curl -s -H "X-aws-ec2-metadata-token: $T" http://169.254.169.254/latest/meta-data/spot/instance-termination-time)
  [ -n "$T" ] && kubectl cordon "$NODE_NAME" && \
    kubectl drain "$NODE_NAME" --ignore-daemonsets --delete-emptydir-data --grace-period=60
  sleep 5   # 可调: 轮询间隔；须远小于通知窗口（阿里云约 5 分钟、AWS 2 分钟）
done
```

Spot 节点池准入三件套（4.2"驱逐容忍"的补全）：

```yaml

- key: spot-pool                  # 可调: 与节点池自定义污点一致（ACK/EKS 均支持）
  operator: Exists
```

### 典型故障案例

某团队成本月增 30% 不知为何。按四环节排查：僵尸 PV 遗留云盘 23 块（≈¥1,800/月）、超配 3 倍以上的副本占 28%、4 台低载节点未回收（≈¥7,200/月）；另把 6 台无状态节点切 Spot（再省 ≈¥3,000/月）。两个月后成本回落 25%。

点评：**成本失控往往是"闲置 + 超配"**，极简 FinOps 四环节就能抓回大量浪费。

### 根因定位

问题的真正发源地是**成本不可见**：没有月账单拆分与分账标签，浪费就永远藏在"反正也就几万块"里。

### 长效治理方案

- 每月账单拆分表 + 环比 >±10% 解释制度。
- 闲置巡检表周期执行，回收走工单（先快照后回收）。
- 超配检测周报 + 单次降幅 ≤30% 纪律。
- 三标签 + namespace 分账月报与业务对齐；专用池利用率纳入巡检。

### 自动化/自治闭环

FinOps 是自治的成本边界：弹性自治若不受成本约束会无限扩容烧钱（1.5 节跳级自治的成本爆炸案例）。本节为 L2 运维自治（15 章）提供"成本可见性"输入，也为 L3 的预算护栏（token 日预算、扩容日上限，15.4⑤）提供口径基础。

### 生产问题

月度复盘会：三份复盘的根因栏都写着"操作失误"，整改栏都写着"加强培训"；而半年前一份同根因的复盘正躺在台账里没人翻。**复盘的产出如果只有会议纪要，故障就只是"过了"而非"学了"**——同类故障反复发生，组织没有变聪明。

### 传统方案失效原因

归因个人、根因肤浅、整改空泛、无长效跟踪——定论不再论证（单次复盘五字段模板与 blameless 制度见 12.3/12.4，本节不重复）。

### 架构约束与权衡

复盘体系的三层分工（本节管第三层）：

| 层 | 归属 | 内容 |
|---|---|---|
| 单次复盘 | 12.3 | 五字段模板、五问根因、止损优先 |
| 组织制度 | 12.4 | 台账、值班授权、周/月复盘节奏 |
| **趋势治理（本节）** | 13.4 | 月度三指标看板、整改闭环率、技术债常态化巡检 |

权衡：趋势治理把复盘从"个案记忆"变成"组织指标"——投入是每月一次 ≤30 分钟评审，换来重复故障归零与技术债显性化。

### 最小可行方案

1. **月度三指标看板**：MTTR 分布、根因分布、整改闭环率，从 12.4 台账自动取数。
2. **闭环率进考核**：当月到期整改项闭环率 <90% 即亮灯。
3. **技术债巡检**：四项一张表（EOL 集群/高危镜像/废弃 chart/低载高配节点），季度进评审。

### 生产落地实现

**① 月度趋势看板字段表**（数据源 = 12.4 故障台账；Grafana 表格面板或工单系统报表，11 章栈）：

| 指标 | 口径 | 健康线 | 越线去向 |
|---|---|---|---|
| MTTR P50 | 台账 P1+ 故障"认领→止损"中位数 | ≤15 min | 超线 → 值班授权/SOP 复查（12.4） |
| MTTR P90 | 同口径 p90 | ≤60 min | 超线 → 升级链路/云厂商通道复查（12.3） |
| 根因分布 | 变更/容量/依赖/硬件/代码 占比饼图 | 变更类 >40% → 发布流程改进 | 指向 10 章灰度；容量类上涨 → 13.2 评审 |

云服务映射：①比对 **ACK/EKS 版本支持矩阵**（云控制台与 CLI 可查）；②镜像漏洞用 **ACR 安全扫描**（对照 ECR 扫描）；④指标来自 node_exporter + 自建 VM 栈（11 章）。数字：四条红线 + 闭环率 ≥90% + MTTR P50 ≤15min/P90 ≤60min。

### 典型故障案例

某误操作删除生产数据。第一份复盘归因"操作失误"、整改"加强培训"——半年后同类事故重演。第二份按五问挖到系统根因（为何单人即有删权限/为何无二次确认/为何恢复靠人肉），整改改为收敛权限 + 准入二次确认 + 自动备份（7.4），并把同类高危操作做进准入校验；该整改项进月度看板按闭环率口径核验生效。此后同类事故归零。

点评：**"操作失误"从来不是根因，是根因的遮羞布**。

### 根因定位

三份复盘都写着"加强培训"，同类故障却每季一次——矛盾本身即是答案：**复盘缺的不是模板，是"根因 → 系统整改 → 趋势闭环"的工程化体系**。

### 长效治理方案

- 月度三指标看板（从台账自动取数），闭环率 <90% 亮灯进考核。
- 技术债四项巡检表周期执行，越红线强制排期。
- 根因沉淀为自治规则/准入校验/告警（反哺 12、15 章）。

### 自动化/自治闭环

复盘是自治的演进引擎：每次故障根因沉淀为自治规则（做进自动处置/准入校验/告警），把"人学到的"变成"系统学到的"——本节是 15.4 复盘迭代环节的组织级输入。
