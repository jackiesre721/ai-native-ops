## 4.1 K8s核心定位：云原生统一操作系统、AI负载统一运行底座

### 生产问题

三套运行底座（虚拟机编排 + 容器编排 + 裸机调度）= 三套监控、三套交付、三倍成本，且故障跨底座无法关联、人才无法复用。这是底座碎片化的直接账单：**每多一种底座，运维复杂度不是相加，是相乘**。

### 传统方案失效原因

- **一负载一底座**：传统服务用虚拟机，容器化服务用容器编排，AI 用裸机直跑，底座随负载类型 proliferate。
- **底座间无统一抽象**：调度、网络、存储、可观测各搞各的，跨底座治理不可能。
- **底座升级各自为政**：三套底座三条升级路径，兼容性风险三倍。
- **AI 负载游离于底座之外**：GPU 直跑裸机，脱离声明式与可观测体系，回到第一代运维（第 1 章）。

失效根因：**没有把 K8s 当作"统一操作系统"来用**。K8s 的核心价值不是"跑容器"，而是提供一个统一的、声明式的、可扩展的运行底座，让所有负载（包括 AI）共享同一套治理范式。

### 架构约束与权衡

K8s 作为统一操作系统的两层定位：

| 定位 | 含义 | 代价 |
|---|---|---|
| **云原生统一操作系统** | 为所有负载提供调度、网络、存储、可观测的统一抽象 | 接受抽象层、学习曲线 |
| **AI 负载统一运行底座** | 通过设备插件/CRD 扩展，让 AI 负载也跑在同一底座上 | 需扩展机制（GPU 调度等） |

权衡的核心：**统一底座牺牲了"为每种负载特调最优"的灵活性，买回了"一套治理范式覆盖所有负载"的可扩展性**。碎片化底座每种最优，但治理成本爆炸；统一底座单种未必最优，但治理线性可控。规模化下，后者完胜。

### 最小可行方案

统一底座的最小落地：

1. **所有负载上 K8s**：传统服务容器化上 K8s，AI 负载通过设备插件上 K8s（第 17 章）。
2. **共享治理平面**：调度、交付（GitOps）、可观测、稳定性治理统一一套。
3. **扩展而非另起**：K8s 不够用的能力（GPU 调度、推理弹性）通过 CRD/Operator/设备插件扩展，不另立底座。

### 生产落地实现

- 传统服务：Deployment/StatefulSet 等标准负载跑在 K8s（第 7 章）。
- AI 负载：GPU 设备插件 + 节点标签 + 推理负载（第 17 章）。
- 统一交付：Helm + ArgoCD 承载所有负载（第 9、10 章）。
- 统一可观测：VictoriaMetrics/Loki/Tempo 采集所有负载指标（第 12 章）。

### 典型故障案例

某团队 AI 推理服务跑在裸机，传统服务跑在 K8s，两者调用链路跨底座断裂。一次推理服务 OOM 导致上游网关报错，定位耗时 25 分钟。把推理服务也迁上 K8s、共享可观测后，同类故障定位压到 3 分钟。

点评：**底座统一 = 治理可视**。跨底座的故障天然是盲区，统一底座让链路贯通。

### 根因定位

根因不在某次定位慢，而在**底座碎片化导致治理割裂**。底座是治理的载体，载体不统一，治理必然碎片化。

### 长效治理方案

- 坚守"所有负载上 K8s"的统一底座原则。
- 能力不足用扩展机制补（CRD/Operator/设备插件），不另立底座。
- 治理平面（调度/交付/观测/稳定性）全负载共享。

### 自动化/自治闭环

统一底座是三层自治的承载平台：**L1 机械自治、L2 运维自治的控制循环都跑在 K8s 上**；L3 智能自治的决策也通过 K8s 扩展机制执行。底座统一，三层自治才能统一作用于所有负载。

### 生产检查清单

- [ ] 是否所有负载（含 AI）都跑在 K8s 上？
- [ ] 治理平面（调度/交付/观测/稳定性）是否全负载共享？
- [ ] K8s 不够用的能力是否通过扩展机制补齐（而非另立底座）？
- [ ] 是否消除了底座碎片化（虚拟机/裸机/容器多套并存）？

## 4.2 控制平面、节点核心组件架构与高可用生产容错逻辑

### 生产问题

一个生产集群的控制平面跑在单节点上，某次 etcd 所在节点故障，整个控制平面不可用，集群无法调度、无法扩缩、无法更新，业务虽在跑但丧失了所有治理能力，持续 40 分钟才恢复。**控制平面是 K8s 的大脑，大脑单点 = 整个治理体系单点**。业务"还在跑"是假象，一旦需要任何控制动作（扩容、重启、更新），立刻停摆。

### 传统方案失效原因

- **控制平面单节点**：apiserver/etcd/scheduler/controller-manager 挤一台，任一组件挂即全局挂。
- **etcd 无冗余**：etcd 是唯一状态存储，单点 etcd 挂 = 集群状态丢失风险。
- **控制面与业务混部**：控制面组件和业务 Pod 抢资源，业务流量洪峰挤垮控制面。
- **无容错设计**：没有多副本、没有反亲和、没有备份，故障即灾难。

失效根因：**把控制平面当普通组件部署，忽视了它是整个集群的可靠性瓶颈**。控制面单点是 K8s 生产部署最经典的坑。

### 架构约束与权衡

控制平面高可用的约束与权衡：

| 组件 | 高可用约束 | 代价 |
|---|---|---|
| **etcd** | 多副本（3/5 奇数）+ 反亲和 + 定期备份 | 资源开销、运维复杂 |
| **apiserver** | 多实例水平扩展 + 负载均衡 | 无状态，易扩展 |
| **scheduler/controller-manager** | 多实例 + leader election | 一主多备，瞬时切换 |
| **控制面/业务隔离** | 控制面专属节点（taint/nodeSelector） | 专属节点成本 |

权衡的核心：**高可用用资源换可靠性**。奇数多副本 etcd 满足多数派写入了；控制面专属节点隔离爆炸半径。对生产集群，这是非选项的基线。

### 最小可行方案

最小高可用配置：

1. **etcd 3 节点奇数集群**，跨可用区反亲和，定期快照备份。
2. **apiserver 多实例** + 前置负载均衡。
3. **scheduler/controller-manager** 多实例 + leader election（默认行为）。
4. **控制面专属节点**（托管 K8s 由云厂商保障；自建需 taint 隔离）。

### 生产落地实现

- 托管 K8s（如 ACK/EKS/GKE）：控制面由云厂商托管高可用，团队聚焦节点与业务。
- 自建 K8s：etcd 静态 pod 多副本 + 反亲和 + Velero/etcdctl 定期快照（快照是 8.4 节容灾范围）。
- 控制面隔离：控制面组件 nodeSelector/taint 钉专属节点，priorityClass 保护不被抢占。
- etcd 备份：定期快照进对象存储，定期演练恢复（8.4 节）。

### 典型故障案例

单节点 etcd 故障导致控制面全挂的事故，在迁到 3 节点 etcd + 跨可用区反亲和后，再未出现全局失控。某次一个 etcd 成员故障，多数派仍可用，集群治理能力零中断。

点评：**控制面高可用不是"锦上添花"，是"底线"**。单点控制面等于把整个集群的可靠性赌在一个节点上。

### 根因定位

根因不在某次节点故障，而在**控制面无冗余设计**。组件单点是架构问题，不是运气问题。

### 长效治理方案

- 控制面组件强制多副本 + 反亲和。
- etcd 强制定期备份 + 恢复演练。
- 控制面与业务节点隔离，专属节点保护。
- 托管优先（能托管不自建），降低控制面运维负担。

### 自动化/自治闭环

控制面高可用是 L1 机械自治的运行基础：**控制循环（第 5 章）依赖控制面持续运转**。控制面挂了，调谐闭环就停了，机械自治失效。所以控制面可靠性是整个自治体系的底座。

### 生产检查清单

- [ ] etcd 是否多副本（奇数）+ 跨可用区反亲和？
- [ ] etcd 是否定期快照备份并演练恢复？
- [ ] apiserver 是否多实例 + 负载均衡？
- [ ] 控制面是否与业务节点隔离（专属节点/taint）？
- [ ] 是否优先采用托管 K8s 降低控制面运维风险？

## 4.3 调度器、API、控制器架构定位与生产权衡（不展开内部调谐机制，与第5章严格分层）

### 生产问题

团队不理解 K8s 内部"谁干什么"，出问题不知该查哪个组件：Pod 卡 Pending 不知是调度器问题还是资源不足；声明了副本数却没生效，不知是控制器问题还是 API 问题。**对三大核心组件的职责边界不清，导致排障像盲人摸象**，每个组件都被怀疑一遍，耗时翻倍。

### 传统方案失效原因

- **把 K8s 当黑盒**：只会用 `kubectl`，不懂背后哪个组件负责什么，排障无方向。
- **职责混淆**：以为调度器和控制器是一回事，以为 API server 只是"转发"，出了问题乱猜。
- **不知道生产权衡点**：调度器默认策略够不够、API server 能撑多少 QPS、控制器热升级会不会丢调谐，全凭感觉。

失效根因：**只学"怎么用"，不学"谁在管"**。生产排障和容量规划要求理解组件职责与权衡，黑盒思维撑不住生产。

### 架构约束与权衡

三大核心组件的职责分层（本章只讲定位与权衡，调谐机制细节归第 5 章）：

| 组件 | 职责定位 | 生产权衡点 |
|---|---|---|
| **API server** | 唯一入口，所有读写经它，无状态，水平扩展 | QPS/请求速率、etcd 写入瓶颈、准入控制开销 |
| **调度器** | 决定 Pod 跑哪个节点（资源/亲和/污点） | 调度延迟、大规模集群调度吞吐、自定义调度器需求 |
| **控制器** | 驱动实际状态向期望状态收敛（第 5 章详述） | 调谐频率、热升级期间调谐连续性、多控制器竞争 |

权衡的核心：**三者分工是 K8s 声明式模型能 scale 的关键**——API server 统一入口保证一致性，调度器专注节点选择，控制器专注状态收敛。理解分工，才能在生产中精准定位问题组件、合理规划容量。

### 最小可行方案

生产认知与排障的最小框架：

1. **入口认知**：所有 `kubectl`/CI/ArgoCD 操作都经 API server，API server 慢 = 全局慢。
2. **调度认知**：Pod Pending 先查调度器决策（资源不足/亲和不满足/污点）。
3. **收敛认知**：声明不生效查对应控制器（Deployment/StatefulSet controller）。
4. **权衡点监控**：API server QPS、调度延迟、控制器调谐延迟纳入观测（第 12 章）。

### 生产落地实现

- 排障路径：现象 → 定位组件（API/调度器/控制器）→ 查该组件日志/指标。
- API 容量：监控 API server 请求速率与延迟，超限扩 apiserver 副本或优化客户端（列表请求加 watch/分页）。
- 调度容量：大规模集群关注调度吞吐，必要时开调度器批量调度或自定义调度器（AI 算力场景，第 17 章）。
- 控制器连续性：控制器升级期间关注调谐是否中断（热升级机制，第 5 章）。

### 典型故障案例

某集群大规模扩容时 Pod 大量 Pending，团队以为是资源不足，加节点无效。实际是调度器在高并发下调度延迟飙升（调度吞吐瓶颈）。优化调度器配置（批量调度）后缓解。

点评：**不懂组件职责，排障会查错方向**。这次误判浪费了两小时和一批无用节点。

### 根因定位

根因不在调度器配置，而在**对组件职责与权衡的认知缺失**。黑盒思维让排障变成穷举猜测。

### 长效治理方案

- 团队掌握三大组件职责边界与排障路径。
- 组件关键指标（API QPS、调度延迟、调谐延迟）持续观测。
- 容量规划基于组件权衡点（不是凭感觉）。
- 调谐机制的深入理解统一归第 5 章，本章只立定位。

### 自动化/自治闭环

三大组件是 L1 机械自治的执行机构：**API server 接收期望状态，控制器驱动收敛，调度器分配资源**（第 5 章详述闭环）。本章的职责分层，是理解第 5 章调谐闭环运转的前提。

### 生产检查清单

- [ ] 团队是否清晰掌握 API/调度器/控制器三者职责边界？
- [ ] 是否有 API server QPS/延迟、调度延迟、调谐延迟的观测？
- [ ] Pod Pending 是否能快速定位到调度器决策原因？
- [ ] 容量规划是否基于组件权衡点（而非感觉）？
- [ ] 是否避免把三大组件混为一谈？

## 4.4 K8s版本生命周期、跨版本滚动升级、兼容性风险治理规范

### 生产问题

一个集群停留在已 EOL（停止维护）的 K8s 版本两年没升级，某次新发现的控制面高危 CVE 无官方补丁，被迫在压力下紧急跨多个大版本升级，踩了一堆 API 弃用和废弃的坑，升级过程业务多次抖动。**版本欠债是 K8s 运维的"技术债利息"——越拖越贵，最终被迫在高风险下硬升级**。

### 传统方案失效原因

- **不升级**：怕升级出事，能拖就拖，版本越来越旧，欠债越积越多。
- **跨大版本升级**：平时不升，一升跳好几个版本，API 弃用/废弃/行为变化集中爆发。
- **无兼容性预检**：升级前不检查已弃用 API，升级时才发现 Helm chart/Operator 不兼容，中途卡死。
- **无滚动策略**：全量升级，控制面与业务同时变，出事无法隔离。

失效根因：**把版本升级当一次性大工程而非常态化纪律**。K8s 一年两到三个小版本，社区只维护最近几个，不跟随 = 必然欠债。

### 架构约束与权衡

版本治理的约束与权衡：

| 约束 | 含义 | 代价 |
|---|---|---|
| **跟随社区节奏** | 定期升级，不停留在 EOL 版本 | 持续升级投入 |
| **逐版本滚动** | 不跨大版本跳级，一次一小版本 | 升级频率高但每次低风险 |
| **兼容性预检** | 升级前扫描弃用 API/废弃特性 | 需要工具与流程 |
| **控制面/业务分阶段** | 先升控制面，再滚动节点/业务 | 升级周期长但可隔离 |

权衡的核心：**常态化小步升级的累计成本，远低于欠债后硬升级的一次性风险**。频繁但低风险 > 罕见但高风险。

### 最小可行方案

版本治理的最小纪律：

1. **不碰 EOL**：跟踪社区支持周期，集群版本始终在支持范围内。
2. **小步快跑**：一次升一个小版本，不跳级。
3. **升级前预检**：扫描弃用 API（`kubectl deprecations` 等工具），修复不兼容项。
4. **分阶段滚动**：先控制面，再分批节点，业务通过 PDB 保护（第 7 章）。

### 生产落地实现

- 版本策略：托管 K8s 跟随云厂商推荐版本节奏；自建跟随上游小版本。
- 兼容性预检：升级前用工具扫描集群在用的已弃用 API，清单化修复。
- 滚动升级：控制面先升（托管自动/自建逐节点），节点分批 drain/升级，业务 PDB 保证最少可用副本。
- 回滚预案：升级前备份 etcd，出问题可回滚控制面（8.4 节）。

### 典型故障案例

某团队跨两个大版本升级，中途发现核心 Operator 依赖的 API 已被移除，Operator 全挂，业务受影响。被迫回滚，升级失败。如果平时小步升级，弃用 API 会在第一次升级时就被预检发现，不会集中爆发。

点评：**版本欠债的利息，总是在最不想付的时候被强制收取**。

### 根因定位

根因不在某次升级失败，而在**缺乏常态化版本治理纪律**。不跟随社区节奏，欠债必然积累，最终高风险硬升级。

### 长效治理方案

- 集群版本始终在社区支持范围内（不碰 EOL）。
- 小版本滚动升级，不跳级。
- 升级前强制兼容性预检。
- 控制面/节点/业务分阶段滚动 + PDB 保护 + etcd 备份回滚。

### 自动化/自治闭环

版本治理是底座持续可靠的保障：**控制面与节点持续跟随社区，机械自治（第 5 章）才运行在受支持的、有补丁的基础上**。版本欠债的集群，连安全补丁都拿不到，自治体系建立在沙地上。

### 生产检查清单

- [ ] 集群版本是否在社区/云厂商支持范围内（非 EOL）？
- [ ] 是否常态化小版本升级（不跨大版本跳级）？
- [ ] 升级前是否扫描并修复已弃用 API？
- [ ] 升级是否分阶段（控制面→节点→业务）+ PDB 保护？
- [ ] 升级前是否有 etcd 备份与回滚预案？

## 4.5 K8s原生架构短板与生产适配边界（进阶架构思维）

### 生产问题

团队把所有运维期望寄托在 K8s 原生能力上，结果撞上原生短板：多集群没有原生舰队管理、HPA 只懂 CPU 不懂业务指标、网络默认无租户强隔离、AI 算力调度原生支持弱。**把 K8s 当万能药，遇到原生短板就卡壳，要么硬塞不适配的方案，要么手工打补丁**，治理越来越乱。

### 传统方案失效原因

- **迷信原生**：认为"K8s 原生的就是对的"，忽视它的能力边界。
- **硬塞方案**：用 HPA（CPU 驱动）硬套业务弹性需求，结果失配（第 7 章）。
- **手工补丁**：原生不够用就写脚本绕过，破坏声明式一致性。
- **不识别边界**：不知道哪些该用原生、哪些该用扩展、哪些该等 V2。

失效根因：**没有建立"原生能力边界"的认知**。K8s 是强大但有限的操作系统，把它的边界当无穷，必然在边界处翻车。

### 架构约束与权衡

K8s 主要原生短板与适配策略（进阶思维，明确边界）：

| 短板 | 原生现状 | 适配策略 | 承接 |
|---|---|---|---|
| **多集群舰队** | 无原生舰队管理 | 单集群治理为主，多集群归 V2 | 边界外 |
| **业务驱动弹性** | HPA 只懂 CPU/内存 | KEDA 扩展补齐（第 16 章） | 第 16 章 |
| **网络强隔离** | namespace 是软边界 | NetworkPolicy + 资源配额（附录 A） | 附录 A |
| **AI 算力调度** | 原生支持弱 | 设备插件 + 专有调度（第 17 章） | 第 17 章 |
| **状态存储治理** | 原生 PV/PVC 基础 | 深度 DR 归 V2，本章只到 RPO/RTO | 第 8 章 |

权衡的核心：**原生不够的地方，用云原生扩展机制（CRD/Operator/设备插件）补，而不是手工绕过或另立体系**。识别边界、用对扩展，是进阶架构思维。

### 最小可行方案

边界识别与适配的最小框架：

1. **摸清原生边界**：对每个运维诉求，先判断 K8s 原生是否够用。
2. **够用用原生**：标准负载用原生 Deployment/HPA/Service。
3. **不够用用扩展**：业务弹性用 KEDA、AI 调度用设备插件/专有调度，都走云原生扩展。
4. **超出归 V2**：多集群舰队、深度 DR 等明确划边界，不在 V1.0 硬做。

### 生产落地实现

- 弹性：标准负载 HPA，业务/推理负载 KEDA（第 16 章）。
- 隔离：NetworkPolicy + ResourceQuota + LimitRange（附录 A）。
- AI 调度：GPU 设备插件 + 节点标签 + 专有调度（第 17 章）。
- 多集群/深度 DR：明确归 V2，V1.0 只做单集群治理 + 极简容灾（8.4 节）。

### 典型故障案例

某团队用 HPA（CPU）给消息队列消费者扩缩，CPU 不高但队列积压严重，HPA 不扩容，消费者跟不上。改用 KEDA（队列深度驱动）后，扩缩精准匹配负载。

点评：**识别"HPA 只懂 CPU"这个原生边界，用 KEDA 补齐，是典型的边界适配**。硬塞 HPA 是边界认知缺失。

### 根因定位

根因不在 HPA 配置，而在**没识别原生能力边界**。把原生当无穷，必然在边界处失配。

### 长效治理方案

- 建立"原生 vs 扩展 vs V2"的三层边界认知。
- 原生够用用原生，不够用用云原生扩展，超出归 V2。
- 杜绝手工绕过原生（破坏声明式一致性）。
- 边界认知随 K8s 版本演进定期更新。

### 自动化/自治闭环

边界识别是三层自治分层的基础：**L1 机械自治用 K8s 原生（调谐闭环）；L2 运维自治用扩展（KEDA/SLO）；L3 智能自治针对 AI 短板（推理调度）**。每一层都是"原生不够→扩展补齐"的体现。本章的边界思维，贯穿全书后续所有"用扩展补原生"的决策。

### 生产检查清单

- [ ] 是否摸清了 K8s 在弹性/隔离/AI 调度/多集群等方面的原生边界？
- [ ] 原生不够的地方是否用云原生扩展机制补齐（而非手工绕过）？
- [ ] 多集群舰队、深度 DR 等是否明确划归 V2（不在 V1.0 硬做）？
- [ ] 是否避免了对 K8s 原生能力的迷信（把它当有限操作系统）？
- [ ] 边界认知是否随版本演进定期更新？
