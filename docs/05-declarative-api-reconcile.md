# 第5章 声明式API与控制循环核心机制

## 5.1 命令式运维与声明式运维的思维本质差异（极简导入）

### 生产问题

团队用脚本运维：扩容写 `kubectl scale`、改配置写 `kubectl edit`、修故障写 `kubectl delete pod`。每次操作都是一条一次性命令，**没人知道集群当前的"正确状态"应该是什么**。结果是配置漂移、操作不可复现、故障反复——因为命令式运维只记录"做了什么动作"，不记录"系统应该是什么样"。当系统偏离正轨，没有任何机制把它拉回来，只能靠人再次发命令。

### 传统方案失效原因

命令式与声明式的思维差异，决定了运维体系的天花板：

- **命令式聚焦"动作"**：扩容 = 执行 scale 命令。动作执行完就结束，不保证状态持续。
- **命令式不可重入**：同一条命令执行两次结果可能不同（已扩容再扩容 = 浪费）。
- **命令式无期望状态**：系统该有几个副本、什么配置，只存在于操作者脑中和历史命令里。
- **命令式靠人维持**：状态偏离只能靠人发现并再次下命令，没有自动收敛。

失效根因：**命令式把"状态"和"动作"绑死，且只记录动作**。系统无法自我维持稳态，复杂度全部压在人的记忆力与纪律上。

### 架构约束与权衡

声明式运维的思维本质：

| 维度 | 命令式 | 声明式 |
|---|---|---|
| 关注点 | 做什么动作（how） | 要什么状态（what） |
| 可重入 | 否（重复执行有副作用） | 是（重复执行收敛到同一状态） |
| 期望状态 | 隐式（在操作者脑中） | 显式（写在声明里） |
| 稳态维持 | 靠人 | 靠控制循环持续调谐 |

权衡的核心：**声明式放弃了对"每一步动作的精确控制"，换来了"状态的持续自维持"**。命令式让你精确控制每一步，但状态随时会漂移；声明式你不能控制每一步，但系统能持续向期望状态收敛。规模化运维下，后者是唯一可持续的模式。

### 最小可行方案

思维转换的最小实践：

1. **改写运维心智**：从"我要执行什么动作"转为"我要系统达到什么状态"。
2. **声明写入 Git**：期望状态以 YAML/Helm 形式存 Git，而非临时命令。
3. **让系统去达成**：交给控制器调谐，不手动执行每一步。
4. **验证收敛**：检查实际状态是否等于期望状态，而非检查命令是否执行。

### 生产落地实现

- 扩容：声明 `replicas: 5`（而非 `kubectl scale --replicas=5`），控制器维持 5 个副本。
- 配置：声明 ConfigMap + 挂载（而非登机改文件），Pod 重建自动应用。
- 修复：声明期望状态，控制器把偏离的实际状态拉回（而非手动 delete）。
- 全程声明进 Git，由 GitOps 同步（第 10 章）。

### 典型故障案例

某次值班手动 `kubectl edit` 改了生产配置应急，没记录。两周后 Pod 重建，配置回退到旧值，故障复发。根因是命令式改的没进声明，重建即丢失。改为声明式 + GitOps 后，任何配置变更都进 Git，重建后自动应用正确状态。

点评：**命令式应急改的，必然在下次重建时丢失**。声明式让"正确状态"成为唯一事实，重建不会丢。

### 根因定位

根因不在某次没记录，而在**命令式运维不持久化期望状态**。状态只在动作发生时正确，过后无人维护必然漂移。

### 长效治理方案

- 全面声明式：期望状态进 Git，禁止命令式直改生产。
- 运维心智从"动作"转向"状态"。
- 让控制器维持稳态，人只负责定义期望状态。
- 验证收敛而非验证命令执行。

### 自动化/自治闭环

声明式思维是 L1 机械自治的认知前提：**只有先接受"声明期望状态、让系统调谐"，机械自治闭环才有用武之地**。本节的心智转换，是本章后续调谐闭环（5.2）、稳态自愈（5.3）能够被理解和使用的基础。没有声明式思维，控制器再强也用不起来。

### 生产检查清单

- [ ] 运维心智是否从"执行动作"转向"声明状态"？
- [ ] 期望状态是否全部进 Git（无命令式直改生产）？
- [ ] 是否让控制器维持稳态（而非手动维持）？
- [ ] 验证方式是否是"实际状态 == 期望状态"（而非命令执行成功）？
- [ ] 是否杜绝了"应急手改、重建丢失"的循环？

## 5.2 核心闭环逻辑：期望状态(Desired) → 调谐循环(Reconciliation) → 实际状态(Actual)
<!-- 【机械自治】三层自治第一层核心闭环 -->

### 生产问题

想象没有控制器持续调谐的世界：团队用一次性命令把副本数扩到 5（或直接起 5 个裸 Pod），某节点故障导致 2 个 Pod 随节点消失。**没人盯、没东西补**，实际就停在 3 个，业务降级跑了半天直到用户投诉。"扩到过 5"只是个历史动作，不是当前保证——没有任何机制持续把实际拉回 5。声明式的价值不在"写下来 / 执行一次"，而在"有控制循环持续让实际趋近期望"——这个持续动作就是调谐循环。

> 注：一旦把 `replicas: 5` 写进 **Deployment**，期望状态就持久化进 etcd，Deployment controller 会持续比对并自动补足——这正是本节要讲的闭环，上面是"没有这个闭环"时的痛。

### 传统方案失效原因

- **用了无控制器的资源**（如裸 Pod）或把期望只写进文档：写了"想要 5 个"，但没有控制器持续比对，偏离无人纠正。
- **一次性脚本当调谐**：写个定时脚本检查副本数，但脚本不持续、不可重入、覆盖不全。
- **不理解闭环的持续性**：以为设置一次就够了，不知道稳态需要持续维持。
- **调谐与声明割裂**：声明在 Git，调谐靠人/脚本，两者没形成自动闭环。

失效根因：**没有建立"持续调谐"的闭环**。声明式 + 调谐循环是一个整体，缺了调谐，声明就是死文档。

### 架构约束与权衡

调谐闭环的三个要素与权衡（期望 vs 实际，控制器持续比对纠正）：

```mermaid
flowchart LR
    D([期望状态 Desired]) --> C{控制器<br/>持续比对}
    A[实际状态 Actual] --> C
    C -->|偏离则纠正| ACT[调谐动作]
    ACT --> A
    classDef start fill:#3451b2,color:#fff,stroke:#2a4090,stroke-width:2px
    classDef proc fill:#e0e7ff,stroke:#3451b2,color:#1e3a8a
    classDef decision fill:#fef3c7,stroke:#d97706,color:#78350f,stroke-width:2px
    class D start
    class C decision
    class A,ACT proc
```

| 要素 | 作用 | 权衡 |
|---|---|---|
| **期望状态 (Desired)** | 目标：系统应该是什么样 | 必须显式、可版本化 |
| **实际状态 (Actual)** | 现实：系统现在是什么样 | 必须可观测、持续采集 |
| **调谐循环 (Reconciliation)** | 动作：比对差异并纠正 | 频率与资源开销的权衡 |

闭环逻辑：**控制器持续 watch 资源 → 比对 Desired vs Actual → 有差异则执行动作消除差异 → 循环往复**。最终态：Actual 收敛到 Desired，系统稳态自维持。

权衡的核心：**调谐频率越高，收敛越快，但控制面负载越大**。生产要在收敛速度与控制面开销间取平衡（默认值通常够用，大规模需调优）。

### 最小可行方案

闭环运转的最小理解：

1. **显式声明期望状态**：YAML/Helm 写清目标（副本数、镜像、配置）。
2. **信任控制器调谐**：Deployment controller 等持续比对并纠正。
3. **观测实际状态**：用 `kubectl get` / 监控确认 Actual 收敛到 Desired。
4. **改期望即改状态**：更新声明，控制器自动把 Actual 调到新 Desired。

### 生产落地实现

- 副本维持：`replicas: 5` → 节点故障 Pod 失联 → controller 发现 Actual=3 → 重新调度补足到 5。
- 配置生效：改 ConfigMap → Pod 重建（或滚动）→ 新配置应用。
- 版本更新：改镜像 tag → controller 滚动替换 → Actual 收敛到新版本。
- 自愈：Pod 崩溃 → controller 重启；节点故障 → Pod 重新调度。

### 典型故障案例

节点故障后 Pod 没自动补足的事故，根因是用了裸 Pod（无控制器），裸 Pod 丢了就丢了，没有 controller 调谐。改为 Deployment 后，节点故障自动重调度，副本数秒级恢复。

点评：**调谐闭环依赖控制器**。裸 Pod、无控制器的资源，不在闭环内，故障即丢失。

### 根因定位

根因不在节点故障，而在**资源未纳入控制器的调谐闭环**。闭环覆盖到的资源能自愈，覆盖不到的就靠人。

### 长效治理方案

- 所有负载纳入控制器（Deployment/StatefulSet/Job 等），禁用裸 Pod。
- 期望状态显式声明 + 版本化。
- 实际状态持续可观测。
- 信任调谐循环维持稳态，人退到定义期望。

### 自动化/自治闭环

本节定义的调谐闭环，就是 L1 机械自治的核心引擎：**期望状态 → 调谐循环 → 实际状态收敛**。这个闭环的可靠运转，是基础设施层稳态自愈的保证，也是全书三层自治的地基。L2（第 16 章）和 L3（第 18 章）都建立在"这个底层闭环可信"之上。

### 生产检查清单

- [ ] 所有负载是否都纳入控制器（无裸 Pod）？
- [ ] 期望状态是否显式声明且版本化？
- [ ] 实际状态是否持续可观测？
- [ ] 是否信任控制器调谐（而非手动维持）？
- [ ] 调谐频率在大规模下是否经过评估调优？

## 5.3 K8s机械自治核心：系统稳态自愈、资源收敛逻辑与生产容错机制
<!-- 【机械自治】基础设施层稳态自愈 -->

### 生产问题

团队理解了调谐闭环，但生产里还是频繁出事：节点 NotReady 没被及时处理导致 Pod 卡死、滚动更新配置不当导致服务中断、控制器热升级时调谐暂停引发短暂失控。**知道"有闭环"和"闭环在生产里可靠运转"是两回事**——机械自治要真正稳，需要理解它的收敛逻辑和容错边界。

### 传统方案失效原因

- **不理解收敛逻辑**：不知道控制器如何处理部分失败、并发冲突、最终一致性。
- **容错配置缺失**：PDB、优雅终止、健康探针没配，机械自治的自愈动作反而造成中断。
- **忽视热升级窗口**：控制器/APIServer 升级期间调谐可能暂停，没预案。
- **误把机械自治当万能**：以为有了闭环就不用观测，实际闭环本身也需要被观测。

失效根因：**只用了闭环的"形"，没掌握闭环的"理"**。收敛逻辑和容错边界不清，机械自治在生产里就不可靠。

### 架构约束与权衡

机械自治的收敛逻辑与容错机制：

| 机制 | 作用 | 权衡 |
|---|---|---|
| **最终一致性** | 闭环持续调谐，最终收敛（不保证瞬时一致） | 收敛期间状态可能短暂偏离 |
| **幂等调谐** | 调谐动作可重复执行，结果一致 | 需要控制器正确处理并发 |
| **健康探针** | 判定 Pod 是否健康，触发自愈 | 探针配置不当会误杀 |
| **PDB** | 保护自愿中断时的最少可用副本 | 与滚动更新/驱逐的协调 |
| **优雅终止** | 终止前处理在途请求/清理 | 需配 `preStop` + grace period |

权衡的核心：**机械自治用"最终一致 + 持续调谐"换取稳态自愈，代价是收敛期间的短暂偏离需要被观测和容忍**。容错机制（探针/PDB/优雅终止）则是让自愈动作本身不造成二次故障。

### 最小可行方案

可靠机械自治的最小配置：

1. **三探针齐全**：liveness（崩溃自愈）、readiness（流量就绪）、startup（慢启动保护）。
2. **PDB 保护**：关键服务设 PDB，保证滚动/驱逐时最少可用副本。
3. **优雅终止**：配 `preStop` 钩子 + 合理 `terminationGracePeriodSeconds`（第 17、18 章对 AI 负载尤其重要）。
4. **闭环可观测**：调谐延迟、重启次数、NotReady 节点纳入监控（第 12 章）。

### 生产落地实现

- 自愈：liveness 探针失败 → 重启；节点 NotReady → Pod 重调度（需控制器覆盖）。
- 容错：PDB 防止自愿中断下副本不足；`maxUnavailable`/`maxSurge` 控制滚动节奏。
- 优雅终止：`preStop` 处理在途请求（推理服务的在途请求，第 18 章），grace period 给足清理时间。
- 热升级预案：控制器升级期间关注调谐延迟，关键变更避开升级窗口。

### 典型故障案例

某服务滚动更新时全部副本同时被替换，服务中断 30 秒。根因是没配 PDB + `maxUnavailable: 100%`。配 PDB（minAvailable 保障）+ `maxUnavailable: 1` 后，滚动更新零中断。

点评：**机械自治的自愈动作（滚动替换）若不容错，本身就是故障源**。PDB 和滚动策略让自愈安全。

### 根因定位

根因不在控制器逻辑，而在**容错机制缺失**。闭环会自愈，但自愈动作需要探针/PDB/优雅终止保驾护航，否则自愈变自伤。

### 长效治理方案

- 所有负载三探针齐全 + PDB + 优雅终止。
- 理解最终一致性，容忍短暂偏离，用观测确认收敛。
- 闭环本身纳入观测（调谐延迟/重启次数）。
- 控制器热升级有预案，关键操作避窗口。

### 自动化/自治闭环

本节的容错机制让 L1 机械自治在生产里**可靠**运转：**稳态自愈 + 容错保护 = 可信赖的基础设施层自治**。这个"可信赖"是 L2/L3 的前提——上层自治的决策要交给下层执行，下层必须可靠。机械自治不稳，上层自治就是空中楼阁。

### 生产检查清单

- [ ] 所有负载是否三探针齐全（liveness/readiness/startup）？
- [ ] 关键服务是否配 PDB 保障最少可用副本？
- [ ] 是否配优雅终止（preStop + 合理 grace period）？
- [ ] 滚动策略（maxUnavailable/maxSurge）是否安全？
- [ ] 闭环本身是否纳入观测（调谐延迟/重启次数/NotReady）？
- [ ] 是否理解最终一致性，容忍短暂偏离并用观测确认收敛？

## 5.4 CRD+Operator扩展思想与企业定制化运维落地范式

### 生产问题

团队有大量领域特定的运维诉求（如某个复杂中间件的部署+扩缩+备份+故障恢复），K8s 原生资源（Deployment/StatefulSet）表达不了它的完整生命周期，只能写一堆外部脚本拼凑，又回到命令式运维。**当原生资源不够表达领域逻辑，企业要么手工补丁，要么需要一个能把领域知识编码进集群的扩展机制**——这就是 CRD + Operator。

### 传统方案失效原因

- **原生资源表达力不足**：Deployment 只懂副本维持，不懂"备份""故障转移""版本兼容迁移"等领域逻辑。
- **外部脚本断裂**：领域逻辑写在外部 CI/脚本里，不进集群控制平面，不享受调谐闭环。
- **运维知识无法沉淀**：专家经验留在脚本和脑子里，无法复用、无法标准化。
- **每个团队重复造轮子**：同类中间件，各团队各写一套运维脚本。

失效根因：**没有把领域运维逻辑"编码进集群"**。留在集群外的逻辑，不参与调谐闭环，等于回到第一代运维。

### 架构约束与权衡

CRD + Operator 的扩展思想：

| 概念 | 作用 | 权衡 |
|---|---|---|
| **CRD（自定义资源）** | 定义新的期望状态类型（如 `XxxCluster`） | 需设计合理的 schema |
| **Operator（自定义控制器）** | 用代码实现该资源的调谐逻辑 | 开发与维护成本 |
| **领域知识编码** | 把专家的部署/扩缩/备份/恢复逻辑写进 Operator | 知识沉淀，可复用 |

核心思想：**Operator = 领域专家的运维知识，以控制器形式常驻集群**。它让复杂中间件/数据库/AI 服务也能享受声明式 + 调谐闭环，把"专家运维"变成"系统能力"。

权衡的核心：**Operator 把运维知识从"人/脚本"转移到"集群内控制器"，换来了领域逻辑的声明式治理与自洽运转**。代价是 Operator 本身的开发与维护成本——只对高价值、重复性强的领域逻辑值得做。

### 最小可行方案

先判断该领域**值不值得** Operator 化（不是所有领域都该上 Operator）：

| 管理方式 | 机制 | 适合 | 代价 |
|---|---|---|---|
| **Operator**（CRD + 控制器） | 领域逻辑进集群、持续调谐 | 复杂生命周期（部署+扩缩+备份+恢复）+ 多团队重复 | 开发/维护成本高 |
| **Helm + 脚本**（外部管理） | 一次性部署、外部触发 | 生命周期简单、低频变更 | 能力弱、不持续 reconcile |

**选型**：仅当"生命周期复杂 + 多团队重复"才值得 Operator（重投入）；简单/低频场景 Helm + 脚本就够，别为了 Operator 而 Operator（过度工程）。判定值得后，落地的最小范式：

1. **识别高价值领域**：复杂生命周期（部署+扩缩+备份+恢复）且重复性强的中间件/服务值得做 Operator。
2. **设计 CRD schema**：把领域期望状态建模成自定义资源字段。
3. **实现调谐逻辑**：用 Operator SDK 等实现控制循环，编码部署/扩缩/备份/恢复。
4. **复用与标准化**：成熟 Operator 沉淀为团队/企业标准，避免重复造轮子。

### 生产落地实现

- CRD：定义如 `RedisCluster`、`ModelService` 等领域资源，spec 表达期望状态。
- Operator：实现调谐，处理部署、扩缩、备份、版本升级、故障恢复。
- 声明式管理：领域资源像原生资源一样进 Git，GitOps 同步（第 10 章）。
- AI 场景：AI 推理/训练服务的复杂生命周期也可用 Operator 表达（第 17、18 章相关能力可 Operator 化）。

### 典型故障案例

某数据库集群用 StatefulSet + 外部脚本运维，备份/恢复脚本散落，某次恢复演练发现脚本已失效（依赖版本变了），差点无法恢复。改用成熟数据库 Operator（内置备份/恢复调谐）后，备份恢复成为声明式自洽能力，定期演练零负担。

点评：**Operator 让领域运维从"脚本拼凑"变成"系统能力"**，且因为常驻调谐，能力始终有效。

### 根因定位

根因不在脚本失效，而在**领域逻辑游离于控制平面之外**。不进调谐闭环的逻辑，必然随时间失效。

### 长效治理方案

- 高价值领域逻辑用 Operator 编码进集群。
- 成熟 Operator 沉淀为标准，复用而非重造。
- 领域资源声明式管理（进 Git + GitOps）。
- Operator 本身纳入版本管理与可观测。

### 自动化/自治闭环

CRD + Operator 是机械自治的**扩展机制**：**原生资源不够用时，用自定义资源 + 自定义控制器，把新的"期望状态→调谐→实际状态"闭环纳入系统**。这让机械自治的能力从 K8s 原生负载，扩展到任意领域逻辑（包括 AI 负载的复杂生命周期），是 L1 自治边界的延伸，也为 L2/L3 的治理对象提供了更丰富的载体。

### 生产检查清单

- [ ] 复杂生命周期的中间件/服务是否考虑用 Operator 治理（而非外部脚本）？
- [ ] CRD schema 是否合理表达领域期望状态？
- [ ] Operator 调谐逻辑是否覆盖部署/扩缩/备份/恢复？
- [ ] 成熟 Operator 是否沉淀为标准复用？
- [ ] 领域资源是否纳入声明式 + GitOps 管理？

## 5.5 增强工作负载：原地升级、Pod打散、Sidecar无感注入生产实践

### 生产问题

团队跑着一批特殊负载：AI 推理（大镜像、加载慢）、有状态服务（重启代价高）、多副本需严格打散（避免单节点/单可用区扎堆）。原生工作负载处理这些场景都很吃力：**滚动更新要重建 Pod，大镜像重新加载几分钟；有状态服务频繁重建伤性能；副本扎堆单点故障**。原生工作负载是为通用场景设计的，特殊场景需要增强能力。

### 传统方案失效原因

- **重建式更新代价高**：大镜像 Pod 重建要重新拉镜像+加载模型，分钟级中断。
- **无原地升级**：原生 Deployment 更新 = 重建新 Pod，无法只改镜像/配置而保留 Pod 网络/存储身份。
- **打散能力不足**：默认调度可能把副本扎堆，反亲和需手动配置。
- **Sidecar 管理割裂**：Sidecar（如日志/监控 agent）混在业务 Pod 里，升级要连带业务重建。

失效根因：**原生工作负载的"重建式"模型，对大镜像/有状态/强打散场景不友好**。这些场景需要增强工作负载能力。

### 架构约束与权衡

三类增强工作负载能力：

| 能力 | 作用 | 权衡 |
|---|---|---|
| **原地升级** | 只改镜像/配置，复用 Pod（不重建），秒级生效，保留网络/存储 | 需增强工作负载（如开源 inplace 能力），偏离原生语义 |
| **Pod 打散** | 拓扑分布约束（topologySpreadConstraints），副本跨节点/可用区均匀 | 调度约束增多，资源碎片风险 |
| **Sidecar 无感注入** | Sidecar 独立生命周期（原生 Sidecar，1.28+），升级不连累业务 | 需较新 K8s 版本 |

权衡的核心：**增强能力用复杂度换场景适配**。原地升级避免重建代价但偏离原生；打散提高可用性但增加调度约束。按场景选用，不是全开。

### 最小可行方案

按场景的最小增强配置：

1. **大镜像/AI 推理**：用支持原地升级的工作负载，避免重建重新加载（第 17、18 章）。
2. **多副本可用性**：`topologySpreadConstraints` 跨节点/可用区打散。
3. **Sidecar（日志/监控）**：用原生 Sidecar（1.28+）独立升级，不连累业务。
4. **有状态服务**：StatefulSet + 有序滚动 + PV 保持（第 8 章）。

### 生产落地实现

- 原地升级：对大镜像推理服务，用支持 inplace 的负载（避免每次更新重新拉镜像+加载）。
- 打散：`topologySpreadConstraints: maxSkew: 1`，跨 zone/hostname 均匀分布。
- Sidecar：原生 Sidecar（`restartPolicy` 独立），日志/监控 agent 升级不重建业务容器。
- 反亲和：对关键服务加 `podAntiAffinity`，避免单点扎堆。

### 典型故障案例

某推理服务每次更新重建 Pod，重新加载模型耗时 3 分钟，更新期间容量下降。改用原地升级后，更新只换镜像不重建，加载利用既有缓存，中断从分钟级降到秒级。

点评：**重建式更新对大镜像/AI 负载是奢侈品**。原地升级是这类场景的生产刚需。

### 根因定位

根因不在更新策略，而在**原生重建式模型与特殊负载特性不适配**。特殊场景需要增强能力，硬用原生必然代价高。

### 长效治理方案

- 大镜像/AI 负载用原地升级工作负载。
- 关键服务强制拓扑打散 + 反亲和。
- Sidecar 用原生 Sidecar 独立生命周期。
- 有状态服务有序滚动 + PV 保持。

### 自动化/自治闭环

增强工作负载让机械自治在特殊场景下**依然高效**：**原地升级让大镜像负载的更新不破坏稳态；打散让自愈后的副本分布依然高可用；Sidecar 无感升级让治理组件升级不影响业务稳态**。这些能力拓宽了 L1 机械自治的适用边界，是 AI 负载（第 17、18 章）能够高效自愈的支撑。

### 生产检查清单

- [ ] 大镜像/AI 负载是否用原地升级（避免重建重新加载）？
- [ ] 关键服务是否配拓扑打散（topologySpreadConstraints）+ 反亲和？
- [ ] Sidecar 是否用原生 Sidecar 独立升级（不连累业务）？
- [ ] 有状态服务是否有序滚动 + PV 保持？
- [ ] 增强能力是否按场景选用（非全开）？
