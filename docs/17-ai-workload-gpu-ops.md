## 17.1 AI异构算力生产体系：GPU设备插件、算力池化、调度核心运维逻辑（不讲解CUDA、SM、NVLink等硬件底层原理）

### 生产问题

团队上线 AI 推理，把 GPU 节点加进 K8s 集群，但 K8s 默认只懂 CPU/内存，根本认不出 GPU——Pod 申请 GPU 资源失败、调度器不知道哪些节点有 GPU、多个 AI Pod 在一个 GPU 上挤成一团。**异构算力（GPU）对默认 K8s 是"看不见、调不动、管不住"的**，AI 负载根本跑不起来。

### 传统方案失效原因

- **K8s 默认不懂 GPU**：没有设备插件，GPU 对调度器不可见。
- **算力不可调度**：无法按 GPU 类型/数量调度 Pod。
- **无算力池化**：GPU 独占分配，利用率低（一个 Pod 占整卡，浪费）。
- **运维靠裸机**：GPU 跑在 K8s 外（裸机），回到第一代运维（第 1 章）。

失效根因：**没有建立"K8s 认得 GPU + 可调度 + 可池化"的异构算力生产体系**。本章纯运维视角，不展开 CUDA/SM/NVLink 硬件原理（归 V2）。

### 架构约束与权衡

异构算力生产体系（运维视角）：

| 维度 | 机制 | 权衡 |
|---|---|---|
| **GPU 可见** | 设备插件让 K8s 认得 GPU | 插件运维 |
| **算力可调度** | 节点标签 + GPU 资源调度 | 调度复杂度 |
| **算力池化** | 多实例共享/切分 GPU（如 MIG/vGPU） | 共享 vs 隔离 |
| **运维在 K8s 内** | GPU 负载上 K8s，不裸机 | 接受抽象 |

权衡的核心：**异构算力要纳入 K8s 治理（认得/调度/池化），而非裸机游离**。池化提升利用率但有隔离权衡，按负载特性选。

### 最小可行方案

异构算力最小体系：

1. **GPU 可见**：装 GPU 设备插件，节点 GPU 对 K8s 可见可申请。
2. **算力可调度**：GPU 节点打标签（GPU 型号/数量），Pod 按 GPU 资源 + 节点标签调度。
3. **算力池化**：按需用 GPU 切分/共享（提升利用率），独占用于性能敏感负载。
4. **纳入 K8s**：AI 负载跑在 K8s，共享可观测/交付/弹性（第 3 章统一底座）。

### 生产落地实现

- 设备插件：NVIDIA GPU Operator/Device Plugin，节点 GPU 注册为可申请资源（`nvidia.com/gpu`）。
- 调度：GPU 节点 `nodeSelector`/污点（专用节点，7 章），Pod 申请 GPU 资源。
- 池化：MIG/时间分片等让多 Pod 共享 GPU（利用率敏感场景）；独占分配（性能敏感场景）。
- 统一底座：AI 负载 Deployment/Rollout + GitOps + 可观测（10、12 章）。

### 典型故障案例

AI 推理 Pod 申请 GPU 一直 Pending，根因是未装 GPU 设备插件，K8s 不认 GPU 资源。装 GPU Operator 后，GPU 可见可申请，Pod 正常调度。

点评：**GPU 对 K8s 默认是隐形的**，设备插件是让算力"可见可调度"的第一步。

### 根因定位

根因不在 Pod 配置，而在**未建立异构算力生产体系（K8s 不认 GPU）**。

### 长效治理方案

- GPU 设备插件让算力可见可申请。
- GPU 节点标签 + 污点专用调度。
- 按负载特性池化/独占。
- AI 负载纳入 K8s 统一治理（不裸机）。

### 自动化/自治闭环

异构算力纳入 K8s 是 L3 智能自治（第 18 章）的**算力底座**：**L3 要对 AI 负载做智能调度/弹性，前提是算力对 K8s 可见可调度**。算力游离在 K8s 外（裸机），L3 无从作用。本章让算力进入 K8s 治理域，是 L3 自治可作用的范围前提。

### 生产检查清单

- [ ] 是否装了 GPU 设备插件（K8s 认得 GPU）？
- [ ] GPU 节点是否打标签 + 污点专用调度？
- [ ] 是否按负载特性选择池化/独占？
- [ ] AI 负载是否纳入 K8s（不裸机）？
- [ ] 算力是否对调度器"可见可调度可申请"？

## 17.2 GPU资源精细化管控：配额隔离、显存资源治理、算力负载均衡策略

### 生产问题

GPU 节点上的负载互相挤占：一个 Pod 吃满显存导致同 GPU 其他 Pod OOM、算力负载不均（有的 GPU 满载有的空闲）、配额失控（某团队占满 GPU 影响他人）。**GPU 资源不精细化管控，要么 OOM 互踩要么利用率不均**，昂贵的 GPU 被浪费或争抢。

### 传统方案失效原因

- **无配额**：GPU 资源无 namespace 配额，某负载占满影响他人。
- **显存不治理**：显存超用导致 OOM，同 GPU Pod 互踩。
- **负载不均**：无算力负载均衡，GPU 冷热不均。
- **粗放分配**：整卡独占分配，利用率低。

失效根因：**GPU 资源没有"配额隔离 + 显存治理 + 负载均衡"的精细化管控**。

### 架构约束与权衡

GPU 资源精细化管控：

| 维度 | 机制 | 权衡 |
|---|---|---|
| **配额隔离** | ResourceQuota 限 GPU（7 章）+ 切分 | 隔离 vs 利用率 |
| **显存治理** | 监控显存用量，防 OOM 互踩 | 安全 vs 利用率 |
| **负载均衡** | 算力调度均衡 GPU 利用 | 均衡 vs 调度复杂 |

权衡的核心：**GPU 精细化管控在"隔离安全"与"利用率"间平衡**——配额/显存隔离保安全，池化/负载均衡提利用率。

### 最小可行方案

GPU 分配策略先按"隔离强度 vs 利用率"选型（三种机制不同，别混为一谈）：

| 策略 | 机制 | 隔离/性能 | 适合 |
|---|---|---|---|
| **独占**（整卡一 Pod） | 一卡一负载 | 最强隔离、性能可预测 | 性能敏感推理 / 训练 |
| **MIG** | **硬件空间分区**（固定切片） | 硬隔离、粒度固定 | 多负载需强隔离、粒度能匹配 |
| **时间分片**（MPS / time-slicing） | **时分共享**（交替执行） | 高密度、隔离弱、互相影响 | 利用率优先、负载可容忍干扰 |

**选型**：性能敏感 → 独占；需硬隔离且粒度匹配 → MIG；追求利用率、负载可接受互相影响 → 时间分片。注意 MIG 是硬件空间切分、时间分片是时分共享，**机制不同、代价不同**，按负载特性选，不是"随便挑一个池化方式"。

精细化管控其余最小集：

1. **配额**：namespace GPU 配额（7 章 ResourceQuota），防某负载占满。
2. **显存治理**：监控显存用量 + 告警，防 OOM 互踩；按所选策略隔离。
3. **负载均衡**：调度时按 GPU 利用率均衡分布（避免冷热不均）。
4. **监控**：GPU 利用率/显存纳入可观测（12 章 + 18 章）。

### 生产落地实现

- 配额：ResourceQuota 限每 namespace GPU 数（7 章）。
- 显存：监控显存（DCGM/exporter，18 章详细），告警防 OOM；MIG/切分隔离。
- 负载均衡：调度器按 GPU 利用率（节点扩展资源）均衡，或专用调度插件。
- 监控：GPU 指标进 VictoriaMetrics（12、18 章）。

### 典型故障案例

同 GPU 上两个推理 Pod，一个显存超用导致另一个 OOM 重启。监控显存 + 切分隔离后，互踩消除。

点评：**显存是 GPU 共享的头号互踩点**，不治理就 OOM 不断。

### 根因定位

根因不在某次 OOM，而在**GPU 资源未精细化管控**。粗放分配必然互踩或浪费。

### 长效治理方案

- GPU 配额（ResourceQuota）。
- 显存监控 + 告警 + 切分隔离。
- 算力负载均衡调度。
- GPU 利用率/显存纳入可观测。

### 自动化/自治闭环

GPU 精细化管控是 L3 智能自治（第 18 章）的**资源治理基础**：**L3 的动态调度/弹性决策，依赖 GPU 资源的可观测与可控（配额/显存/均衡）**。资源不可控，L3 的调度决策无依据、易失控。本节让 GPU 资源可度量可管控，L3 才能基于它做智能调度。

### 生产检查清单

- [ ] 是否有 GPU namespace 配额？
- [ ] 显存是否监控 + 告警 + 切分隔离？
- [ ] 算力负载是否均衡调度（无冷热不均）？
- [ ] GPU 利用率/显存是否纳入可观测？
- [ ] 是否避免显存互踩 OOM？

## 17.3 AI模型专属运维：大体积镜像构建、高速分发、模型存储与版本溯源（完整承接第2章迁移内容，边界永久固定）

### 生产问题

AI 模型动辄几十 GB，镜像/模型文件巨大：构建慢、拉取慢（分钟级甚至更久）、存储成本高、版本混乱。某次推理更新，拉取大模型镜像耗时许久，节点磁盘被塞满，更新期间容量下降。**大体积模型资产让第 2 章的容器供应链遇到新挑战**——构建/分发/存储/版本都需专门方案。

### 传统方案失效原因

- **大镜像普通构建**：几十 GB 镜像普通 Docker build，慢且大。
- **慢拉取**：每节点拉大镜像，耗时 + 占带宽 + 占磁盘。
- **模型与镜像耦合**：模型打包进镜像，更新模型 = 重建镜像，慢。
- **版本混乱**：模型文件散落，无版本溯源。

失效根因：**没有为 AI 模型资产建立专属的构建/分发/存储/版本运维**。第 2 章通用供应链不够，需 AI 专属方案（边界永久固定：本章承接第 2 章迁移内容）。

### 架构约束与权衡

AI 模型专属运维：

| 维度 | 方案 | 权衡 |
|---|---|---|
| **构建** | 模型与运行镜像分离（运行镜像小 + 模型外挂） | 解耦 vs 一体 |
| **分发** | 模型存对象存储/专用分发，运行时拉取 | 分发快 |
| **存储** | 模型存对象存储/PVC，不进镜像 | 成本低 |
| **版本溯源** | 模型即制品，版本化进仓库 | 可追溯 |

权衡的核心：**模型与运行镜像解耦**——运行镜像保持小（第 2 章精简），模型作为独立制品存对象存储/仓库，运行时挂载/拉取。这样更新模型不必重建镜像，分发快、存储省、版本清晰。

### 最小可行方案

AI 模型专属运维最小集：

1. **模型与镜像分离**：运行镜像只含框架（小），模型作独立制品。
2. **模型存对象存储**：模型存对象存储/模型仓库，运行时拉取或挂载。
3. **高速分发**：用模型仓库/CDN/本地缓存加速分发。
4. **版本溯源**：模型即制品，带版本，发布可追溯（GitOps 同步模型版本，第 10 章）。

### 生产落地实现

- 分离：运行镜像（vLLM/SGLang 框架，小，第 2 章精简）+ 模型（独立制品）。
- 存储：模型存对象存储（OSS/S3）或专用模型仓库（如 HF/MLflow 风格）。
- 分发：运行时从对象存储拉模型到本地缓存，或用 PVC 挂载共享。
- 版本：模型带版本标签，部署清单声明模型版本，GitOps 同步（第 10 章）。

### 典型故障案例

某推理把 30GB 模型打包进镜像，每次模型更新重建镜像 + 全节点重拉，更新一次 15 分钟。改"运行镜像小 + 模型对象存储外挂 + 版本化"后，更新只换模型版本（运行时拉取），分钟级完成。

点评：**模型与镜像解耦是 AI 运维的关键**，让模型更新不再等于镜像重建。

### 根因定位

根因不在镜像大，而在**模型与运行镜像耦合 + 无专属分发存储方案**。

### 长效治理方案

- 模型与运行镜像分离（运行镜像精简，模型独立制品）。
- 模型存对象存储/模型仓库。
- 高速分发（对象存储 + 本地缓存/PVC）。
- 模型版本化 + GitOps 同步（可追溯）。
- 边界永久固定：本章承接第 2 章迁移内容，不外扩。

### 自动化/自治闭环

AI 模型专属运维是 AI 负载生命周期（3.4 节）"模型归档→模型仓库→服务部署"环节的落地：**模型作为版本化制品，让 AI 负载的交付也享受声明式 + GitOps + 可追溯**（与第 9、10 章一脉相承）。这把 AI 模型资产纳入统一治理，是 L3 智能自治对 AI 负载可作用的交付基础。

### 生产检查清单

- [ ] 模型是否与运行镜像分离（运行镜像精简）？
- [ ] 模型是否存对象存储/模型仓库（不进镜像）？
- [ ] 分发是否高速（对象存储 + 缓存/PVC）？
- [ ] 模型是否版本化 + GitOps 同步（可追溯）？
- [ ] 模型更新是否不再等于镜像重建？

## 17.4 AI推理服务基础运维：部署规范、保活机制、负载适配、故障快速重启

### 生产问题

AI 推理服务的运维比普通服务难：部署后模型加载慢（启动期长）、保活难（长空闲被误判杀）、负载适配难（GPU 资源与请求特性匹配）、故障重启代价高（重新加载模型耗时许久）。**用普通服务的运维方式套推理服务，部署/保活/负载/重启处处踩坑**。

### 传统方案失效原因

- **忽视启动期**：模型加载耗时，普通 readiness 探针过早判定未就绪。
- **保活误杀**：长空闲期被 liveness 误判（推理空闲 ≠ 死）。
- **负载适配差**：GPU 资源与请求特性（上下文长度/并发）不匹配。
- **重启代价高**：故障重启 = 重新加载模型，慢且影响可用。

失效根因：**没有为 AI 推理服务建立专属的部署/保活/负载/重启规范**（3.2 节三类负载差异）。

### 架构约束与权衡

AI 推理服务基础运维：

| 维度 | 规范 | 权衡 |
|---|---|---|
| **部署** | 原地升级（避免重建重加载，5 章）+ 启动期保护 | 复杂 vs 快 |
| **保活** | startup 探针保护加载期 + 合理 liveness | 保活 vs 误杀 |
| **负载适配** | 按请求特性（上下文/并发）配 GPU 资源与并发 | 适配 vs 通用 |
| **故障重启** | 快速重启（模型预加载/缓存）+ 优雅终止 | 速度 vs 资源 |

权衡的核心：**推理服务运维围绕"模型加载代价高"这一核心特性**——所有规范都为减少加载/重启代价、适配推理负载特性。

### 最小可行方案

推理服务运维最小集：

1. **部署**：原地升级（5.5 节）避免重建重加载；启动期 startup 探针保护。
2. **保活**：startup 探针（加载期 liveness 暂停）+ 合理 liveness（不误杀空闲）。
3. **负载适配**：按请求特性（上下文长度/并发）配 GPU 资源与推理并发参数。
4. **故障重启**：模型本地缓存（重启不重下）+ 优雅终止（处理在途请求，6 章）+ 快速重启。

### 生产落地实现

- 部署：支持原地升级的负载（5.5 节）；startup 探针保护模型加载期。
- 保活：startup（成功前 liveness 暂停）+ liveness（判定推理进程死活，非空闲）。
- 负载适配：vLLM/SGLang 并发参数（max batch/并发）+ GPU 资源匹配请求特性（18 章详细）。
- 重启：模型本地缓存（对象存储拉一次，重启复用）+ `preStop` 优雅终止 + readiness 控制流量。

### 典型故障案例

某推理服务每次更新重建 Pod，重新加载模型 3 分钟，更新期容量骤降。改原地升级 + 模型本地缓存后，更新秒级、重启不重加载。

点评：**推理服务的运维核心是"减少模型加载代价"**，原地升级 + 缓存是关键。

### 根因定位

根因不在某次更新慢，而在**用普通服务运维套推理服务，忽视模型加载特性**。

### 长效治理方案

- 原地升级 + startup 探针保护加载期。
- 保活不误杀（startup + 合理 liveness）。
- 负载按请求特性适配（并发/GPU 资源）。
- 模型本地缓存 + 优雅终止 + 快速重启。

### 自动化/自治闭环

推理服务基础运维是 L3 智能自治（第 18 章）的**运行底座**：**L3 的动态调度/弹性决策，依赖推理服务能快速部署/重启/适配负载**。本节让推理服务可被高效运维，L3 的自治动作（扩缩/重调度）才不会因加载代价过高而失效。

### 生产检查清单

- [ ] 是否用原地升级（避免重建重加载）？
- [ ] 是否 startup 探针保护模型加载期？
- [ ] 保活是否不误杀（合理 liveness）？
- [ ] 负载是否按请求特性适配（并发/GPU 资源）？
- [ ] 故障重启是否快速（模型缓存 + 优雅终止）？

## 17.5 AI算力FinOps极简模型：GPU利用率优化、闲时算力复用、推理单Token成本管控（聚焦运维治理，不扩成本体系）

### 生产问题

GPU 极贵，但团队的 GPU 利用率低下：推理服务闲时 GPU 空转（成本浪费）、利用率不度量（不知贵在哪）、单 Token 成本不知（无法优化）。**GPU 成本失控且不可度量，AI 负载的经济性无法保证**。14.3 节的通用 FinOps 不够，GPU 需专属极简模型。

### 传统方案失效原因

- **利用率低**：推理闲时 GPU 空转，无闲时复用。
- **不度量**：GPU 利用率/单 Token 成本不度量，优化无依据。
- **无单 Token 成本视角**：只看 GPU 花费，不看单位产出（Token）成本。
- **通用 FinOps 不够**：14.3 节通用模型不覆盖 GPU 特性。

失效根因：**没有针对 GPU 的极简 FinOps（利用率/闲时复用/单 Token 成本）**。本章聚焦运维治理，不展开复杂 FinOps 平台（归 V2）。

### 架构约束与权衡

AI 算力 FinOps 极简模型：

| 维度 | 极简实践 | 权衡 |
|---|---|---|
| **利用率优化** | 监控 GPU 利用率，批处理/共享提升 | 利用率 vs 性能 |
| **闲时复用** | 推理闲时复用 GPU 跑训练/批处理 | 复用 vs 调度复杂 |
| **单 Token 成本** | 度量每 Token 成本，指导优化 | 度量 vs 简单 |

权衡的核心：**AI 算力 FinOps 聚焦"利用率 + 闲时复用 + 单 Token 成本"三件事**，让昂贵 GPU 的经济性可度量可优化。不展开复杂平台。

### 最小可行方案

AI 算力 FinOps 极简最小集：

1. **利用率优化**：监控 GPU 利用率（18 章 DCGM 指标），低利用率负载考虑共享/批处理。
2. **闲时复用**：推理闲时（夜间）复用 GPU 跑训练/批处理（错峰）。
3. **单 Token 成本**：度量"每 Token 成本"（GPU 花费 / Token 产出），作为优化北极星。

### 生产落地实现

- 利用率：DCGM 采 GPU 利用率进 VM（12、18 章），低利用率负载优化。
- 闲时复用：推理闲时调度训练/批处理任务到同 GPU（错峰，需调度配合）。
- 单 Token 成本：统计 GPU 成本（14 章 FinOps 分摊）+ Token 产出（推理指标，18 章），算单 Token 成本。

### 典型故障案例

某推理 GPU 利用率长期 < 30%（闲时空转），单 Token 成本高昂。闲时复用 GPU 跑训练 + 提升利用率后，单 Token 成本降 40%。

点评：**GPU 闲时空转是 AI 成本最大浪费**，闲时复用 + 利用率优化是杠杆。

### 根因定位

根因不在 GPU 贵，而在**无 AI 算力 FinOps（利用率/复用/单 Token 成本）**。不度量不优化，成本必然失控。

### 长效治理方案

- GPU 利用率监控 + 优化（共享/批处理）。
- 推理闲时复用 GPU（错峰训练/批处理）。
- 单 Token 成本度量（GPU 成本 / Token 产出）作为优化北极星。
- 复杂 FinOps 平台归 V2，V1.0 用极简模型。

### 自动化/自治闭环

AI 算力 FinOps 是 L3 智能自治（第 18 章）的**成本约束**：**L3 的动态调度若不约束成本，可能过度扩容烧钱（1.5 节案例）**。单 Token 成本作为 L3 决策的约束指标，让智能自治在性能与成本间平衡。这也是第 3 章"成本可控"目标的落地。

### 生产检查清单

- [ ] GPU 利用率是否监控 + 优化（共享/批处理）？
- [ ] 推理闲时是否复用 GPU（错峰训练/批处理）？
- [ ] 是否度量单 Token 成本（GPU 成本/Token 产出）？
- [ ] 是否避免 GPU 闲时空转浪费？
- [ ] 是否明确复杂 FinOps 平台归 V2（V1.0 用极简模型）？
