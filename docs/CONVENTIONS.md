## 三、技术栈选型：双层参考栈（云生态主栈 + 自建平台栈）

**基础设施层（云托管，V1.1 主栈）**——K8s 底座与云资源全部落在托管服务上：

| 能力 | 阿里云（主参考） | AWS（对照） | 为什么不自建（仅一句对照） |
|---|---|---|---|
| K8s 控制面 | ACK（标准托管/Pro） | EKS | kubeadm：控制面 SLA、升级、备份全自担 |
| Pod 云身份 | RAM + RRSA | IAM + IRSA | 长期 AK/SK 塞集群：泄露面大，禁用 |
| 负载均衡 | SLB/NLB（CCM 自动建）、ALB Ingress | ELB/NLB、ALB Ingress | 自建 LB：无云 SLA 与跨 AZ 能力 |
| 存储 | 云盘 CSI / NAS CSI / OSS CSI | EBS / FSx / S3（Mountpoint） | local PV：仅缓存类数据可用 |
| 网络 CNI | Terway（Pod 直通 VPC） | VPC CNI | Flannel/Calico：不合托管主栈，不讲 |
| 镜像仓库 | ACR 企业版 | ECR | 自建 Harbor：同步/扫描/高可用全自建 |
| 节点 | ECS 节点池（自动修复/升级/抢占式） | 托管节点组 / Fargate | 裸机自管：驱动/升级/替换人力高 |

**平台层（自建锁死栈，原理去工具化）**——可观测/交付/AI 推理仍用自建锁死栈，它跑在云托管底座之上：

| 类别 | 参考实例 | 原理（与组件无关，换栈照样适用） |
|---|---|---|
| **可观测栈** | VictoriaMetrics（指标）、Loki（日志）、Tempo（链路）、OpenTelemetry（采集）、Grafana（可视化） | 三支柱协同 + trace ID 关联 + 低成本存储 + 统一可视化 |
| **交付栈** | Helm、ArgoCD、Argo Rollouts | 声明式 + Git 真相源 + 持续同步 + 渐进发布 + 风险护栏 |
| **智能引擎栈（V1.11 定名）** | LLM API（阿里云百炼 DashScope 主参考、AWS Bedrock 对照）+ 建议式分诊器（15.4⑤） | 意图理解 + 多步推理 + 建议式输出（LLM 在环、人在回路、执行在白名单） |

> 云上同样有托管可观测（ARMS / CloudWatch / AMP）、托管交付（AppFlow 类），本书锁死自建栈的取舍在各章用一张「托管 vs 自建」小决策表说明，不展开对比（归 V2）。

## 四、精神内核（全书唯一核心主线）

现代生产运维体系，从人工操作演进为**声明式、可观测、可治理、可自治的生产控制系统**，逐层完成资源控制、交付控制、观测控制、稳定性控制、能力控制、智能决策控制。

## 十、写作句式变体（治模板疲劳）

**共识话题不讲为什么（治通识，最高优先级）**：凡业界已定论的事（Docker 淘汰、声明式优于命令式、不可变优于可变、GitOps 优于 push、SLO 价值、配置漂移有害…），"生产问题 / 传统方案失效"压缩到 1–3 句一笔带过（可直接写"定论，不再论证"），字数预算让给"**怎么做（配置/参数）+ 什么会坏（坑/边界）**"。目标读者是有经验的运维——不需要被说服，需要被填坑。示范：6.1。

10 步模板固定，但**开头与根因的句式必须轮换**，避免全书 80+ 小节千篇一律。每写一节，从下表选一种与相邻小节不同的风格：

**「生产问题」开头变体（不要每次都用"团队/某团队…"）：**

| 风格 | 切入方式 | 示例小节 |
|---|---|---|
| 场景叙事 | 一个具体现场/时刻切入 | 12.1（凌晨告警）、1.1（支付网关） |
| 数据冲击 | 用数字/对比砸开场 | 4.1（三套底座=三倍成本） |
| 认知纠偏 | 抛反直觉现象/疑问 | 6.5（CPU 不忙却过载）、11.1（指标串不上 trace） |
| 团队困境 | 经典"团队…"（保留，但不连续用） | 多数小节 |

**「根因定位」变体（不要每次都"根因不在 X，而在 Y"）：**

- 换主语："问题的真正发源地是…" / "拆到底，是 … 缺位"。
- 换结构：先给结论再解释，或先抛矛盾再点破。
- 偶用"根因不在 X 而在 Y"（有力，但全书不超过 1/3 的小节）。

**「自动化/自治闭环」回扣分级（治回扣过度）：**

- 理论核心章（5 / 16）：完整展开与本层关系。
- 其他章：压成一句"本节为 L? 的 XX 环节"，不重复 L1/L2/L3 定义。

## 十一、DDIA 写作六法（V1.3 新增，学习《设计数据密集型应用》）

> 六法是对 10 步模板的"内容质法"：模板管结构，六法管思想质量。示范章：第 5 章。

1. **反例构造（anomaly-first）**：核心机制先用"精心构造的静默失败场景"检验——描述场景，让读者先猜结果，再揭晓机制为什么赢/输。思想实验与真实故障案例（典型故障案例步骤）是两类素材：前者制造认知冲突，后者提供经验证据。**每个理论核心章至少一个思想实验**。示范：5.1 的"断网的 scale 命令"、5.2 的"错过事件的事件驱动控制器"。
2. **权衡必答"取决于什么"**：凡给出选型结论，必须列出决策变量（规模/团队技能/成本/风险偏好/时间窗，≥3 个）——DDIA 从不单答案，只回答"它取决于 A、B、C"。已有决策表的章节把"变量"显式成列；没有的补一张小表。
3. **保证等级声明**：每个核心机制给「承诺什么 / 不承诺什么」两列表（收敛性、时限、顺序、统计置信）——让读者拿到的是**确切契约**而非模糊安全感。这是 DDIA 隔离级别讲法（read committed/serializable 各自保证什么）的移植。示范：5.3 调谐闭环保证等级表。
4. **数字给体感**：关键数字必须带工程体感对照（"47s 自愈=用户刷新一次页面的时间；210s=用户已经提完工单"；"0.1% 错误预算=每月 43 分钟"）。裸数字不进正文。
5. **贯穿案例宇宙**：见第七节术语——同一虚构公司、同一组服务贯穿全书，示例之间互相成为上下文。
6. **章末知识收拢**：理论核心章（5/16）在最后一节「生产检查清单」之后放一个引用块「本章知识收拢」——3 条读者应能脱稿复述的结论（DDIA 的 Summary 段移植），随后按 V1.10 加「下一章预告」（第 15 章为「全书收束」）；常规章不强制收拢，只加「下一章预告」。
