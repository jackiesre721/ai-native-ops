## 15.1 平台工程核心定位：不是搭建运维平台，而是屏蔽基础设施复杂度、统一生产运行标准

### 生产问题

团队让每个业务团队自己搞定部署、监控、弹性、安全，结果每个团队各搞一套，重复造轮子、质量参差、标准不一。开发者被困在基础设施细节里（写一堆 YAML、配监控、调资源），没精力写业务。**没有平台工程，基础设施复杂度全部压在业务团队，重复 + 不一致 + 低效**。

### 传统方案失效原因

- **复杂度下放**：基础设施复杂度直接扔给业务团队，每个团队重新踩坑。
- **重复建设**：部署/监控/弹性各团队各写一套，N 倍重复。
- **标准不一**：各团队方案不同，全局治理（安全/可观测/成本）难落地。
- **认知误区**：把"平台工程"理解为"搭一个运维平台产品"，偏离本质。

失效根因：**没有用平台工程"屏蔽复杂度 + 统一标准"**。本书明确：平台工程核心不是搭产品，而是抽象与标准化。

### 架构约束与权衡

平台工程核心定位：

| 维度 | 定位 | 权衡 |
|---|---|---|
| **屏蔽复杂度** | 把基础设施复杂度封装，业务只关心业务 | 抽象成本 vs 业务效率 |
| **统一标准** | 部署/观测/稳定性/安全统一标准，全公司一致 | 标准化 vs 灵活 |
| **非搭产品** | 重思想与抽象，非重型平台产品（无 Backstage 等） | 轻 vs 重 |

权衡的核心：**平台工程用"抽象 + 标准"换业务团队效率与全局一致性**。代价是平台抽象的前期投入，换来的是业务团队聚焦业务、全局标准统一。

### 最小可行方案

平台工程最小定位：

1. **抽象复杂度**：把部署/观测/弹性/安全的最佳实践封装成黄金路径，业务只填业务参数。
2. **统一标准**：全公司用统一的基础 chart（9.4 节）、统一可观测（12 章）、统一安全基线（附录 A）。
3. **去产品化**：用轻量抽象（chart 模板/脚本/CRD），非重型平台产品。

### 生产落地实现

- 抽象：基础 chart（9.4 节）封装部署/探针/资源/网络/监控最佳实践，业务 chart 继承只填 values。
- 标准：统一可观测栈（12 章）、统一安全基线（附录 A）、统一交付（GitOps，10 章）。
- 去产品：用 chart/CRD/脚本抽象，不引入重型平台产品（Backstage 等归 V2）。

### 典型故障案例

某公司让 20 个业务团队各自搞部署监控，结果 20 套方案、重复劳动、全局安全审计无法落地。建平台工程（统一 chart + 统一可观测 + 黄金路径）后，业务团队只填业务参数，部署监控质量统一，全局治理可落地。

点评：**平台工程的杠杆在"抽象复用 + 统一标准"**，而非搭一个花哨的平台产品。

### 根因定位

根因不在业务团队能力差，而在**基础设施复杂度未被平台抽象屏蔽**。复杂度下放必然重复低效。

### 长效治理方案

- 平台工程聚焦"屏蔽复杂度 + 统一标准"。
- 用基础 chart/CRD 抽象最佳实践（黄金路径）。
- 全公司统一可观测/安全/交付标准。
- 去产品化（轻量抽象，非重型平台）。

### 自动化/自治闭环

平台工程是自治能力的**抽象载体**：**自治（机械/运维/智能）的能力，通过平台封装成黄金路径，业务团队无需理解自治细节即可享受自治收益**。平台把三层自治的能力标准化输出，是自治规模化的关键。第 16 章的运维自治，正是通过平台固化为业务可用的能力。

### 生产检查清单

- [ ] 基础设施复杂度是否被平台抽象屏蔽（业务只填业务参数）？
- [ ] 是否有黄金路径封装部署/观测/弹性/安全最佳实践？
- [ ] 全公司是否统一可观测/安全/交付标准？
- [ ] 平台是否去产品化（轻量抽象，非重型平台）？
- [ ] 业务团队是否能聚焦业务（不被基础设施细节困住）？

## 15.2 平台工程核心链路：复杂基础设施 → 标准化Platform API → 业务黄金路径 → 研发自助服务 → 统一运行时规范

### 生产问题

团队想建平台工程，但不清楚"平台"到底由哪些环节构成、怎么串起来。结果是东拼西凑的工具堆，没有清晰链路，开发者自助体验差，运行时规范仍不统一。**平台工程没有清晰的核心链路，就退化成工具杂烩**。

### 传统方案失效原因

- **工具堆砌**：买了一堆工具堆成"平台"，无清晰链路。
- **无标准化 API**：平台能力没有统一抽象，业务集成难。
- **无黄金路径**：开发者无标准路径，各自摸索。
- **无运行时规范**：跑起来的东西仍不统一。

失效根因：**没有把平台工程组织成"基础设施→API→黄金路径→自助→规范"的核心链路**。

### 架构约束与权衡

平台工程核心链路：

| 环节 | 作用 | 权衡 |
|---|---|---|
| **复杂基础设施** | 真相：底层复杂的 K8s/IaC/可观测 | 不变 |
| **标准化 Platform API** | 把底层能力抽象成统一接口 | 抽象成本 vs 易用 |
| **业务黄金路径** | 标准化、推荐的开发交付路径 | 标准 vs 灵活 |
| **研发自助服务** | 开发者按黄金路径自助交付 | 自助 vs 管控 |
| **统一运行时规范** | 所有跑起来的服务遵循统一规范 | 一致 vs 多样 |

权衡的核心：**核心链路把"复杂底层"逐步转化为"简单自助 + 统一规范"**，每一步抽象都在降低业务团队负担、提升全局一致性。

### 最小可行方案

核心链路最小落地：

1. **Platform API**：用基础 chart/CRD 把底层能力（部署/观测/弹性/安全）抽象成统一接口。
2. **黄金路径**：定义标准交付路径（继承基础 chart + 填 values + GitOps）。
3. **自助服务**：开发者按黄金路径自助交付，无需运维介入。
4. **运行时规范**：所有服务跑出来都带统一探针/资源/网络/监控（基础 chart 保证）。

### 生产落地实现

- Platform API：基础 chart + CRD（如标准化 Service 抽象）封装能力。
- 黄金路径：`继承基础 chart → 填 values → Git 提交 → GitOps 同步`（9、10 章）。
- 自助：开发者按模板自助，运维只在 chart/平台演进时介入。
- 规范：基础 chart 强制注入统一探针/资源/网络策略/ServiceMonitor（12 章）。

### 典型故障案例

某团队平台是工具堆，开发者集成难、体验差，最终绕过平台各搞各的。重构为清晰链路（统一 chart API + 黄金路径 + 自助）后，开发者乐于用平台自助交付，规范自动统一。

点评：**平台工程的价值在"清晰链路带来的自助体验"**，工具堆砌不等于平台。

### 根因定位

根因不在工具不够，而在**平台工程无清晰核心链路**。无链路的平台是工具杂烩，无法支撑自助。

### 长效治理方案

- 建立"基础设施→API→黄金路径→自助→规范"核心链路。
- Platform API 用基础 chart/CRD 抽象。
- 黄金路径标准化交付。
- 自助服务让开发者自服务。
- 运行时规范由基础 chart 强制保证。

### 自动化/自治闭环

核心链路是自治能力**流向业务的通道**：**自治能力封装在 Platform API（基础 chart/CRD），通过黄金路径让业务自助获得，最终所有服务运行时统一具备自治能力**。没有这条链路，自治只是运维的内部能力，无法惠及业务；有了链路，自治成为业务的默认能力。

### 生产检查清单

- [ ] 是否有标准化 Platform API（基础 chart/CRD 抽象底层）？
- [ ] 是否有清晰的业务黄金路径？
- [ ] 开发者是否能按黄金路径自助交付？
- [ ] 运行时规范是否由基础 chart 强制统一？
- [ ] 平台是否是清晰链路（非工具堆砌）？

## 15.3 交付、观测、稳定性、安全能力的轻量化平台封装范式

### 生产问题

团队有交付、观测、稳定性、安全四类能力，但都是"运维懂、业务不懂"的散装能力，业务要用就得找运维手把手配。四类能力未平台封装，业务自助不了，运维成为瓶颈。**核心能力不封装成业务可自助的范式，运维永远是被拖垮的瓶颈**。

### 传统方案失效原因

- **能力散装**：四类能力各自独立，无统一封装。
- **运维手工配**：业务要用靠运维手工配，不可扩展。
- **无自助范式**：业务无法自助，每次依赖运维。
- **封装过重**：要么不封装，要么一封装就上重型平台。

失效根因：**核心能力没有"轻量化平台封装"**。本书主张轻量封装（chart/CRD/模板），非重型平台。

### 架构约束与权衡

四类能力的轻量封装范式：

| 能力 | 轻量封装 | 承接 |
|---|---|---|
| **交付** | 基础 chart + GitOps 黄金路径 | 9、10 章 |
| **观测** | 基础 chart 自动注入 ServiceMonitor/日志采集 | 12 章 |
| **稳定性** | 基础 chart 默认探针/PDB/资源 + KEDA 弹性模板 | 5、7、16 章 |
| **安全** | 基础 chart 默认 NetworkPolicy/非 root/最小权限 | 附录 A |

权衡的核心：**轻量封装把"运维专家能力"固化进基础 chart，业务继承即获得**。封装一次，全业务复用，运维从"逐个手工配"解放。

### 最小可行方案

四类能力轻量封装：

1. **交付封装**：基础 chart 含标准 Deployment/Rollout/Service，GitOps 同步。
2. **观测封装**：基础 chart 自动注入 ServiceMonitor（VM 采集）+ 日志采集配置。
3. **稳定性封装**：基础 chart 默认探针/PDB/资源，可选 KEDA 弹性模板。
4. **安全封装**：基础 chart 默认 NetworkPolicy/非 root/最小 capabilities。

### 生产落地实现

- 交付：基础 chart 模板化 Deployment/Rollout/Service/Ingress（9.4、10、11 章）。
- 观测：基础 chart 含 ServiceMonitor（VM）+ OTel Collector 采集配置（12 章）。
- 稳定性：基础 chart 默认 liveness/readiness/startup 探针 + PDB + 资源 limit（5、7 章）；KEDA ScaledObject 模板（16 章）。
- 安全：基础 chart 默认 NetworkPolicy + securityContext 非 root + drop capabilities（附录 A）。

### 典型故障案例

某业务上线忘了配监控/网络策略/探针，运维逐个补，耗时且易漏。把这些能力固化进基础 chart 后，业务继承即自动获得，遗漏归零。

点评：**轻量封装的杠杆：能力固化进 chart，业务继承即获得，运维一次封装全公司复用**。

### 根因定位

根因不在业务忘配，而在**核心能力未轻量封装进基础 chart**。散装能力必然依赖运维手工、必然遗漏。

### 长效治理方案

- 四类能力（交付/观测/稳定性/安全）固化进基础 chart。
- 业务继承即获得，无需手工配。
- 轻量封装（chart/CRD/模板），非重型平台。
- 能力演进随基础 chart 升级全局生效（9.4 节）。

### 自动化/自治闭环

四类能力封装是自治能力**业务化的最后一公里**：**自治能力（探针自愈/弹性/SLO/安全）封装进基础 chart，业务继承即默认具备自治**。这让自治从"运维专门启用"变成"业务默认拥有"，是自治规模化的关键。第 16 章运维自治的落地，正依赖这种平台封装。

### 生产检查清单

- [ ] 交付能力是否封装进基础 chart（Deployment/Rollout/Service）？
- [ ] 观测能力是否自动注入（ServiceMonitor/日志采集）？
- [ ] 稳定性能力是否默认（探针/PDB/资源/KEDA 模板）？
- [ ] 安全能力是否默认（NetworkPolicy/非 root/最小权限）？
- [ ] 业务继承基础 chart 是否即获得四类能力？

## 15.4 企业极简平台落地案例（无Backstage、无产品化搭建、无平台深度实战）

### 生产问题

团队听说"平台工程"就要上 Backstage/重型 IDP（内部开发者平台），调研选型半年没落地，业务还在手工配。**把平台工程等同于重型平台产品，反而迟迟落不了地**——忘了平台工程的本质是抽象与标准，工具是次要的。

### 传统方案失效原因

- **工具崇拜**：把平台工程等同于某个工具（Backstage 等），调研选型半年。
- **过度产品化**：追求"搭一个完整平台产品"，偏离"抽象 + 标准"本质。
- **忽视轻量**：忘了轻量抽象（chart/CRD）已能解决大部分问题。
- **迟迟不落地**：等"完美平台"，业务一直手工配。

失效根因：**把平台工程复杂化、产品化，忽视轻量落地**。

### 架构约束与权衡

极简平台落地（无 Backstage、无产品化、无深度实战）：

| 维度 | 极简方案 | 边界 |
|---|---|---|
| **核心抽象** | 基础 chart + CRD + GitOps | 轻 |
| **门户** | 文档 + chart 模板 + GitOps 自助（非 Backstage） | 无重型 IDP |
| **落地节奏** | 先抽象后工具，先能用后完美 | 渐进 |

权衡的核心：**本书 V1.0 主张极简平台——用基础 chart/CRD/GitOps 抽象，不上 Backstage/重型 IDP**。先解决"业务自助 + 标准统一"的核心，门户/产品化归 V2。

### 最小可行方案

极简平台落地：

1. **核心抽象**：基础 chart + CRD 封装能力（15.3 节）。
2. **自助门户**：文档 + chart 模板仓库 + GitOps 流程（开发者 fork 模板填 values 提 MR）。
3. **无 Backstage**：不引入重型 IDP，用 GitOps + 文档即门户。
4. **渐进**：先抽象能用，再视需迭代门户。

### 生产落地实现

- 抽象：基础 chart（封装四类能力）+ 业务 chart 模板。
- 门户：模板仓库（README 教程 + 模板 chart）+ GitOps（开发者填 values 提 MR 即自助上线）。
- 无 Backstage：V1.0 不引入，重型 IDP 归 V2。
- 落地：先用 chart 抽象跑通自助，再视痛点迭代。

### 典型故障案例

某团队调研 Backstage 半年没落地，业务一直手工配。改极简方案（基础 chart + 模板仓库 + GitOps 自助）后，2 周落地，业务自助上线，标准统一。后续若需更丰富门户，再评估 V2 的 IDP。

点评：**极简方案 2 周落地的价值，远超"完美平台"半年没落地**。平台工程重思想轻工具。

### 根因定位

根因不在工具不够，而在**把平台工程产品化、复杂化**。本质是抽象与标准，轻量即可落地。

### 长效治理方案

- 极简平台：基础 chart + CRD + GitOps。
- 自助门户用模板仓库 + 文档（非 Backstage）。
- 先抽象能用，再迭代门户。
- 重型 IDP/产品化归 V2。

### 自动化/自治闭环

极简平台让自治能力**快速落地业务**：**用 chart/CRD/GitOps 这种轻量抽象，自治能力（封装在基础 chart）能最快惠及业务**；等重型平台半年不落地，业务反而一直手工。极简落地优先，是自治规模化的务实路径。

### 生产检查清单

- [ ] 平台是否以基础 chart/CRD/GitOps 为核心抽象？
- [ ] 自助门户是否用模板仓库 + 文档（非 Backstage）？
- [ ] 是否避免把平台工程等同于重型 IDP？
- [ ] 是否先抽象能用、再迭代门户？
- [ ] 业务是否能快速自助上线（而非等完美平台）？
