## 2.1 不可变基础设施核心思想与生产约束：杜绝配置漂移、运行时禁改、版本可追溯、故障可复现

### 生产问题

一个 100 节点的集群里，同一个服务在不同节点上行为不一致：A 节点正常，B 节点偶发超时。排查三天，发现 B 节点半年前被某次应急改动过 `sysctl net.core.somaxconn`，没人记录，从此与 A 节点配置漂移。这种"幽灵差异"在生产环境普遍存在——**配置漂移是事故的温床，它让故障变得不可预测、不可复现**。团队每次排障都要先回答一个无解的问题：这台机器现在到底是什么状态？

### 传统方案失效原因

- **运行时可改 = 漂移必然发生**：只要允许登机修改，漂移就只是时间问题。每次应急改动、每次"临时调一下"，都是一次漂移种子。
- **无版本 = 不可追溯**：当前状态怎么来的，无人知晓。回滚到"上一个已知良好状态"无从谈起，因为根本没记录过。
- **不可复现 = 不可诊断**：故障现场一旦被动过就毁了，复盘只能靠日志推测。
- **修复不可重入**：今天的修复脚本，明天在另一台机器上跑结果不一样，因为基线已经变了。

失效根因：**可变基础设施把"状态"和"过程"耦合在一起，且不记录过程**。状态成了无数手工操作的累积，复杂度爆炸，必然失控。

### 架构约束与权衡

不可变基础设施用四条生产约束根治漂移，每条都有代价：

| 约束 | 含义 | 代价 |
|---|---|---|
| **杜绝配置漂移** | 配置来自声明式定义，不来自手工修改 | 放弃"快速登机改一下"的便利 |
| **运行时禁改** | 任何变更通过重建实例完成，不就地修改 | 变更需要走构建-发布流程，单次更慢 |
| **版本可追溯** | 每个运行态对应一个不可变制品版本 | 需要严格的版本与制品管理 |
| **故障可复现** | 任意版本可从制品精确重建 | 要求环境无状态外泄（状态外置） |

权衡的核心：**不可变牺牲了"单次快速修改"，买回了"规模化下的可预测性"**。可变基础设施单点改得快，但 100 个节点各改各的，复杂度指数爆炸；不可变单次慢，但 100 个节点状态完全一致，复杂度线性可控。

### 最小可行方案

落地的最小约束集，逐条可执行：

1. **镜像即运行态**：所有运行依赖打包进 OCI 镜像，节点上不再装运行时依赖。
2. **配置外置 + 版本化**：配置走 ConfigMap/Helm values（声明式），不写进镜像、不落在机器本地。
3. **状态外置**：有状态部分（数据）外置到 PV/对象存储/数据库，实例本身无状态，可随时销毁重建。
4. **变更 = 换镜像/换配置，不就地改**：任何修改都通过重建 Pod 完成。

### 生产落地实现

- 镜像化：服务以镜像形式交付，节点只负责拉取运行（第 2.2 节供应链）。
- 配置声明化：Helm chart + values 表达配置，GitOps 同步（第 9、10 章）。
- 状态外置：PV/PVC 管理持久数据，Pod 可随意重建（第 8 章）。
- 节点本身不可变：节点配置（内核参数、系统包）由 IaC 声明，节点漂移由定期重建消除（节点镜像化 / Cluster Autoscaler 替换）。

### 典型故障案例

某次扩容，新节点上的服务批量超时，老节点正常。根因是新节点镜像与老节点不一致（构建时拉了不同的基础镜像 tag，`latest` 导致漂移）。事后用 `latest` 的地方全部换成不可变 digest 锁定，漂移消失。

点评：**不可变的"不可变"必须是端到端的**——镜像 tag 用 `latest` 等于把可变性从"机器"挪到了"镜像"，漂移没消除只是换了个地方。

### 根因定位

根因不在某次构建失误，而在**不可变约束没有被端到端执行**：只要供应链任何一环允许可变（`latest` tag、运行时 patch、手工 hotfix），漂移就会从那一环渗入。不可变是系统属性，不是局部属性。

### 长效治理方案

- 镜像用 digest 锁定，禁用 `latest` 进生产。
- 配置全声明式，禁止 SSH 改生产（变更走 GitOps）。
- 节点定期滚动重建，消除累积漂移。
- 状态全部外置，实例无状态化。

### 自动化/自治闭环

不可变基础设施是第 5 章机械自治的前提：**控制循环要调谐"期望状态 vs 实际状态"，前提是"期望状态"是确定且不可变的**。如果运行时可随意改动，期望状态就是个移动靶，调谐闭环无从收敛。不可变让"期望状态"凝固，机械自治才能可靠运转。

### 生产检查清单

- [ ] 生产镜像是否全部用 digest 锁定（无 `latest`）？
- [ ] 是否还有 SSH 直改生产的操作？
- [ ] 配置是否全部声明式外置（无机器本地影子配置）？
- [ ] 有状态部分是否全部外置（实例可随时销毁重建）？
- [ ] 节点是否有定期重建机制消除漂移？

## 2.2 容器生产交付供应链极简链路：镜像构建 → 制品仓库 → 版本追踪 → 漏洞扫描 → 生产发布

### 生产问题

团队 CI 直接把构建好的镜像 push 到生产仓库，跳过扫描和版本管控，理由是"赶发布"。结果一个含已知高危 CVE 的镜像进了生产，三天后被安全扫描发现，全量回滚耗时一整天。更糟的是，没人能立刻说清"生产现在跑的是哪个版本、什么时候推上去的、谁推的"。**没有受控供应链的交付，等于把任意未经校验的制品直接送进生产**——这不是快，是裸奔。

### 传统方案失效原因

- **构建即发布，链路无环节**：build 完直接 push 生产仓库，中间没有闸门，任何构建错误直达生产。
- **无版本追踪**：镜像 tag 混乱（`v1`、`test`、时间戳混用），无法回答"生产现在是什么"。
- **无安全校验**：漏洞扫描缺席，CVE 带病上线。
- **无发布门禁**：谁能推、推到哪、什么时间推，全无规则，审计无从谈起。

失效根因：**把"供应链"简化成了"一个 push"**。供应链的价值在于每个环节都是一道校验，砍掉环节等于砍掉防线。

### 架构约束与权衡

受控供应链用五个环节串联，每个环节是一道闸门：

| 环节 | 作用 | 代价 |
|---|---|---|
| **镜像构建** | 可复现地产出制品 | 构建环境标准化成本 |
| **制品仓库** | 制品的唯一可信存放地 | 仓库运维与存储成本 |
| **版本追踪** | 每个制品可追溯（tag/digest/构建来源） | 版本规范纪律 |
| **漏洞扫描** | 上线前拦截已知风险 | 扫描耗时、误报治理 |
| **生产发布** | 受控地从仓库部署到生产 | 发布流程与审批成本 |

权衡的核心：**每个环节增加交付时间，但成倍降低生产事故概率**。极简链路不是砍环节，是让每个环节最小化、自动化、不阻塞。

### 最小可行方案

最小受控链路（五个环节都保留，但各做最轻）：

1. **构建**：多阶段 Dockerfile，构建可复现（2.3 节）。
2. **仓库**：统一企业镜像仓库，生产只从此拉取。
3. **版本**：镜像 tag = `<service>-<git-sha>`，digest 锁定，禁止 `latest`。
4. **扫描**：CI 内嵌漏洞扫描，高危阻断发布。
5. **发布**：GitOps 拉取（第 10 章），发布动作留痕可审计。

### 生产落地实现

- 构建：CI pipeline 内 `docker build` + 推送，tag 取 git commit sha。
- 仓库：企业 Harbor/ACR 等，生产集群只配置该仓库凭据。
- 版本：tag 规范统一，digest 写入部署清单（GitOps）。
- 扫描：Trivy/Grype 等在 push 后扫描，高危 CVE 设质量门禁。
- 发布：ArgoCD 从 Git 同步部署清单到集群，生产状态 = Git 状态。

### 典型故障案例

某次 CI 配置错误，把一个测试镜像打上了生产 tag 直接发布，线上行为异常。因为 tag 命名无规范、发布无门禁，错误制品 10 分钟内推全量。引入"tag = git-sha + 扫描门禁 + GitOps 审批"后，这类误推被结构上杜绝。

点评：**供应链事故几乎都不是技术问题，是流程缺位**。没有门禁的发布，失误必然直达生产。

### 根因定位

根因不在某次 CI 写错，而在**供应链没有受控环节**。每个事故都能映射到某个缺失或被绕过的环节。供应链的可靠性 = 最弱环节的可靠性。

### 长效治理方案

- 五环节全部自动化、全部留痕、全部不可绕过。
- 高危漏洞自动阻断发布，不依赖人工检查。
- 生产制品来源单一（企业仓库），禁止从公网随意拉取。
- 发布全走 GitOps，禁用 kubectl 直推生产。

### 自动化/自治闭环

受控供应链是第 10 章 GitOps 的前置：GitOps 的"唯一可信源"必须建立在"制品可信"之上，而制品可信由供应链保证。供应链 + GitOps 共同构成"变更可控"的闭环——从代码到生产的每一步都可追溯、可校验、可回滚。

### 生产检查清单

- [ ] 镜像构建是否可复现（同输入同输出）？
- [ ] 是否有统一企业镜像仓库，生产只从此拉取？
- [ ] 镜像 tag 是否规范且 digest 锁定（无 `latest`）？
- [ ] 是否有自动化漏洞扫描且高危阻断发布？
- [ ] 发布是否全部走 GitOps（无 kubectl 直推）？

## 2.3 OCI规范、多阶段精简镜像、生产安全构建最小可行实践

### 生产问题

一个服务的镜像有 2.3GB，构建一次要 12 分钟，每次发布拉取镜像耗时显著，节点磁盘被巨型镜像塞满。安全审计还发现镜像里带着完整的编译工具链、SSH 客户端、甚至源码——这些在生产运行时完全用不到，却全是攻击面。**臃肿镜像不只是慢，是安全债 + 存储债 + 性能债的三重负担**。

### 传统方案失效原因

- **单阶段构建**：把编译环境、源码、运行时全打进一个镜像，体积膨胀，攻击面巨大。
- **基于重型基础镜像**：`ubuntu:latest` 起步，带了一堆用不到的系统工具。
- **镜像内藏密钥/源码**：构建期把 secrets 或源码 COPY 进去，泄露风险。
- **不可复现构建**：依赖外部网络拉包，不同时间构建结果不同。

失效根因：**把镜像当"环境快照"而非"最小运行制品"**。快照思维导致什么都往里塞，最终镜像既不安全也不高效。

### 架构约束与权衡

精简安全镜像用一组实践收敛体积与攻击面：

| 实践 | 作用 | 代价 |
|---|---|---|
| **OCI 规范** | 镜像遵循开放标准，可跨仓库/运行时 | 需用符合规范的构建工具 |
| **多阶段构建** | 编译产物与运行时分离，运行镜像只含必要文件 | Dockerfile 稍复杂 |
| **精简基础镜像** | 用 distroless/scratch/alpine，砍掉无用工具 | 调试不便（无 shell） |
| **构建可复现** | 同输入产同样制品 | 需锁依赖版本 |
| **secrets 不入镜像** | 构建期注入，不 COPY 进层 | 需构建期 secret 机制 |

权衡的核心：**镜像越精简越安全高效，但调试越不便**。生产用精简镜像，调试用临时工具镜像或 `ephemeral container`，两者职责分离。

### 最小可行方案

最小安全构建模板（多阶段 + 精简基础 + 可复现）：

1. **多阶段**：builder 阶段编译，runtime 阶段只 `COPY --from=builder` 产物。
2. **精简基础**：runtime 用 distroless 或 alpine，不含 shell 和编译工具。
3. **版本锁定**：基础镜像和依赖都用明确版本/digest，构建可复现。
4. **secrets 外置**：构建期用 CI secret 注入，绝不 COPY 进镜像层。

### 生产落地实现

```dockerfile
# 示例骨架（多阶段 + 精简）
FROM golang:1.22 AS builder
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -o /app ./...

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=builder /app /app
USER nonroot
ENTRYPOINT ["/app"]
```

- 多阶段：builder 产物 `COPY --from`，runtime 不含编译器/源码。
- 精简：distroless 无 shell，攻击面最小。
- 可复现：基础镜像 digest 锁定，依赖 `go.sum` 锁版本。
- nonroot：运行时非 root，符合最小权限（附录 A）。

### 典型故障案例

某镜像内残留编译期用的 `.env` 文件，含数据库密码，被推到公开仓库后泄露。根因是单阶段构建把整个项目目录 COPY 进镜像。改多阶段 + secrets 不入镜像后，泄露面归零。

点评：**镜像层是不可变的，secrets 一旦入层就永久驻留**，即使后续删除也能从历史层恢复。这是镜像安全的硬约束。

### 根因定位

根因不在"忘了删 .env"，而在**构建范式没有分离"构建环境"与"运行制品"**。单阶段构建让运行镜像继承了构建期的全部内容，secrets、源码、工具链全部成为运行时攻击面。

### 长效治理方案

- 强制多阶段构建，运行镜像禁止含编译工具/源码。
- 强制精简基础镜像（distroless/alpine），禁用重型基础。
- 强制 secrets 不入镜像（构建期注入 + 运行时 ESO/KMS，附录 A）。
- 镜像体积与层数设上限，CI 自动校验。

### 自动化/自治闭环

精简安全镜像是供应链自动化的质量基线：**自动化扫描（2.2 节）能拦截的漏洞，前提是攻击面已经被多阶段构建收敛**。镜像本身精简了，扫描才高效、误报才少、自治门禁才可靠。这是"制品可信"的底层支撑。

### 生产检查清单

- [ ] 镜像是否多阶段构建（运行镜像无编译工具/源码）？
- [ ] 基础镜像是否精简（distroless/alpine，无 shell）？
- [ ] 基础镜像与依赖是否 digest/版本锁定（构建可复现）？
- [ ] secrets 是否绝不入镜像层（构建期注入）？
- [ ] 镜像是否以非 root 运行？
- [ ] 是否有镜像体积/层数上限的 CI 校验？

## 2.4 企业镜像仓库权限、版本管控、安全拦截生产规范

### 生产问题

公司用同一个镜像仓库账号给所有团队，权限是"全仓库读写"。某次实习生误删了一个公共基础镜像 tag，导致十几个服务的 CI 集体构建失败，排查两小时。另一个团队把内部镜像 push 到了公开项目，差点外泄。**仓库权限失控，等于把供应链的"唯一可信源"变成"唯一单点故障源"**——一个误操作就能瘫痪整个交付。

### 传统方案失效原因

- **单一账号 + 全权限**：无角色区分，人人能删能改能推。
- **无项目隔离**：所有镜像堆一起，无边界，误操作跨团队传导。
- **无删除保护**：tag 可被覆盖、可被删，制品不可变原则失守。
- **无拉取来源管控**：生产集群可从任意仓库拉取，制品来源不可信。
- **无安全拦截策略**：CVE/策略不达标也能进仓库、上生产。

失效根因：**把仓库当成"存储"而非"治理对象"**。仓库是供应链的中枢，没有治理的仓库是放大的风险。

### 架构约束与权衡

企业仓库治理用四类规范收敛风险：

| 规范 | 作用 | 代价 |
|---|---|---|
| **权限最小化 + 项目隔离** | 按团队/环境分项目，最小权限 | 权限矩阵维护成本 |
| **版本不可变（tag 不可覆盖/删除保护）** | 制品一旦发布不可篡改 | 改制品须换 tag |
| **拉取来源管控** | 生产只从指定仓库拉取 | 需配置镜像来源策略 |
| **安全拦截策略** | 不合规制品（CVE/签名）拒绝入库或上线 | 策略调优、误报治理 |

权衡的核心：**仓库治理增加流程摩擦，但消除"误操作瘫痪全局"的系统性风险**。对一个 10 人团队可能过重，对多团队企业是必需。

### 最小可行方案

最小治理集（四条规范各做最轻）：

1. **项目隔离 + RBAC**：按团队/环境分项目，push/pull 权限分离。
2. **tag 不可变**：开启 immutable tag / 删除保护，制品发布后不可篡改。
3. **生产来源单一**：生产集群只配置企业仓库凭据，禁止公网随意拉取。
4. **入库/上线拦截**：扫描不通过的制品拒绝入库或阻断上线。

### 生产落地实现

- 权限：Harbor/ACR 的项目 + 角色，CI 用专用 service account（只推特定项目）。
- 不可变：开启仓库的 tag immutability，production 项目 tag 锁定。
- 来源：生产集群 `imagePullSecret` 只指向企业仓库，准入策略（附录 A）校验来源。
- 拦截：仓库内置或外接扫描器，高危 CVE 标记或阻断；签名校验（cosign 等）作为可选项纳入策略。

### 典型故障案例

实习生误删公共基础镜像 tag 导致 CI 集体失败的事故，在开启"production 项目 tag 不可变 + 删除需审批"后彻底消失。即便误操作，仓库也会拒绝执行。

点评：**仓库治理的价值在"让误操作执行不了"**。靠人小心不如靠系统拒绝，这是治理的本质。

### 根因定位

根因不在实习生粗心，而在**仓库缺少不可变与权限治理**。治理缺位时，任何人的任何操作都可能成为全局故障。治理到位时，错误操作被结构上拒绝。

### 长效治理方案

- 权限矩阵定期审计，遵循最小权限（附录 A.1）。
- production 制品强制不可变。
- 生产来源强制单一 + 准入校验。
- 安全拦截策略随威胁演进，定期更新基线。

### 自动化/自治闭环

仓库治理是供应链自治的门禁层：**自动化扫描（2.2 节）的拦截决策，要落到仓库的入库/上线策略上才有效**。仓库既是制品存储，也是自治策略的执行点——不合规制品在仓库环节就被拒绝，无需人工介入。这让供应链具备了"自筛"能力。

### 生产检查清单

- [ ] 仓库是否按团队/环境项目隔离 + RBAC 最小权限？
- [ ] production 制品是否开启 tag 不可变 / 删除保护？
- [ ] 生产集群是否只从指定企业仓库拉取（准入校验）？
- [ ] 是否有入库或上线的安全拦截策略（CVE/签名）？
- [ ] 权限矩阵是否定期审计？
