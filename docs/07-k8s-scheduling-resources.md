## 7.1 Pod生命周期、三大探针机制与异常重启、崩溃根因定位

### 生产问题

服务频繁重启，CrashLoopBackOff 闪个不停，但没人说得清为什么：是程序崩了、是探针太严、是依赖没起、还是资源不够。**Pod 异常重启是最常见的生产故障，但根因五花八门，没有探针与生命周期视角，排查只能在日志里大海捞针**。

### 传统方案失效原因

- **探针缺失或乱配**：没探针（崩了不知道）、探针太严（健康也杀）、探针太松（死了不重启）。
- **不区分探针职责**：liveness/readiness/startup 混用，该限流的重启了，该重启的限流了。
- **不理解生命周期阶段**：Pending/ContainerCreating/Running/Terminating 各阶段卡点不同，混为一谈。
- **崩溃根因不分层**：代码 bug、依赖缺失、资源不足、探针配错都表现为重启，不分类无法定位。

失效根因：**把探针当可选项、把生命周期当黑盒**。探针和生命周期是 Pod 可靠性的主动防线，不用好就是被动救火。

### 架构约束与权衡

三大探针的职责分工：

| 探针 | 职责 | 触发动作 | 误配后果 |
|---|---|---|---|
| **liveness** | 容器是否健康（死没死） | 失败 → 重启 | 太严：健康也重启；太松：死了不重启 |
| **readiness** | 容器是否就绪（能接流量吗） | 失败 → 摘流量（不重启） | 太严：正常也摘流量 |
| **startup** | 慢启动保护（首次就绪前不跑 liveness） | 成功前 liveness 暂停 | 缺失：慢启动服务被 liveness 误杀 |

权衡的核心：**探针是"健康判定"的工程化**——liveness 管"死活"，readiness 管"可用"，startup 管"启动保护"。三者职责清晰，误配任一都会制造故障。

### 最小可行方案

探针与生命周期治理的最小实践：

1. **三探针齐全**：liveness（重启）+ readiness（流量）+ startup（慢启动服务必配）。
2. **探针阈值合理**：基于真实启动时间与响应延迟设定，勿抄默认。
3. **生命周期卡点排查**：Pending（调度/资源）、ContainerCreating（镜像/挂载）、CrashLoopBackOff（代码/依赖/探针）分类定位。
4. **崩溃根因分层**：看 events + 日志 + 资源，分代码/依赖/资源/探针四类。

### 生产落地实现

- 探针配置：HTTP/TCP 探针 + 合理 initialDelaySeconds/periodSeconds（慢启动配 startup）。
- 生命周期：`kubectl describe` 看 events 定位卡点阶段。
- 崩溃定位：CrashLoopBackOff → 看日志（代码/依赖）→ 看 events（探针/调度）→ 看资源（OOM）。
- OOM 定位：`OOMKilled` 状态 + 内存 limit 调优。

### 典型故障案例

某 Java 服务启动需 90 秒，liveness 探针 60 秒就触发重启，陷入无限重启循环。加 startup 探针（保护启动期）后，liveness 在 startup 成功后才生效，服务正常启动。

点评：**慢启动服务不配 startup 探针，就是给 liveness 递刀**。

### 根因定位

根因不在程序，而在**探针职责不清 + 缺少 startup 保护**。探针误配是 CrashLoopBackOff 的高发根因，常被误判为程序 bug。

### 长效治理方案

- 三探针齐全，职责清晰，阈值基于真实数据。
- 慢启动服务强制配 startup 探针。
- 生命周期卡点分类排查（按阶段）。
- 崩溃根因分层定位（代码/依赖/资源/探针）。

### 自动化/自治闭环

探针是机械自治的**健康信号源**：**liveness 触发的重启、readiness 触发的摘流量，都是 L1 机械自治的自愈动作**（第 5 章）。探针准确，自愈才准确；探针误配，自愈变自伤。本节的探针治理，直接决定机械自治的可靠性。

### 生产检查清单

- [ ] 是否三探针齐全且职责清晰？
- [ ] 慢启动服务是否配 startup 探针？
- [ ] 探针阈值是否基于真实启动时间/延迟（非抄默认）？
- [ ] 崩溃是否按生命周期阶段 + 根因分层排查？
- [ ] OOM 类重启是否定位到内存 limit 调优？

## 7.2 核心控制器生产选型：无状态、有状态、守护进程、任务调度适配场景

### 生产问题

团队所有服务都用 Deployment，包括数据库、消息队列、日志采集器、定时任务。结果：数据库 Pod 重建丢了网络身份导致连接断裂、日志采集器没全节点覆盖、定时任务多副本重复执行。**控制器选型错误，让负载跑在不匹配的工作负载模型上，每个特性都被破坏**。

### 传统方案失效原因

- **一刀切用 Deployment**：无状态、有状态、节点级、任务全用 Deployment，特性全错配。
- **不理解控制器差异**：Deployment/StatefulSet/DaemonSet/Job 各自适配不同场景，混淆导致选错。
- **有状态当无状态跑**：数据库/队列用 Deployment，丢失稳定网络身份与有序性。
- **任务当服务跑**：一次性任务用 Deployment，多副本重复执行或永不结束。

失效根因：**没有按负载特性选控制器**。四类控制器各有设计目标，错配必然破坏负载特性。

### 架构约束与权衡

四类核心控制器的适配场景：

| 控制器 | 适配场景 | 关键特性 | 错配后果 |
|---|---|---|---|
| **Deployment** | 无状态服务（API/网关） | 随机 Pod 名、可随意替换 | 跑有状态：丢身份 |
| **StatefulSet** | 有状态服务（数据库/队列） | 稳定网络身份、有序启停、持久 PV 绑定 | 跑无状态：过度复杂 |
| **DaemonSet** | 节点级服务（日志/监控/网络 agent） | 每节点一个 | 跑普通服务：覆盖错 |
| **Job/CronJob** | 一次性/定时任务（批处理/训练） | 跑完即止、重试、并发控制 | 跑成服务：永不结束/重复执行 |

权衡的核心：**控制器选型 = 给负载匹配合适的"生命周期模型"**。选对，控制器特性正好满足负载需求；选错，控制器特性反而破坏负载。

### 最小可行方案

控制器选型的最小规则：

1. **无状态**（API/网关）→ Deployment。
2. **有状态**（数据库/队列/需稳定身份）→ StatefulSet。
3. **节点级**（日志/监控/网络 agent）→ DaemonSet。
4. **任务**（批处理/训练/定时）→ Job/CronJob。

### 生产落地实现

- Deployment：Web/API 服务，配合 HPA 弹性。
- StatefulSet：数据库/消息队列，稳定身份 + PV 持久（第 8 章）。
- DaemonSet：日志/监控/网络 agent，每节点覆盖。
- Job/CronJob：批处理/定时任务/AI 训练任务（第 17 章），配重试与并行度。

### 典型故障案例

某数据库用 Deployment，Pod 重建后 IP 变了，上游连接全断。改 StatefulSet（稳定网络身份 + 有序）后，重建不影响连接。

点评：**有状态负载用 Deployment 是经典翻车**。StatefulSet 的稳定身份是有状态服务的前提。

### 根因定位

根因不在数据库配置，而在**控制器选型错配**。负载特性与控制器模型不匹配，必然破坏稳定性。

### 长效治理方案

- 按负载特性选控制器（无状态/有状态/节点级/任务）。
- 有状态强制 StatefulSet（稳定身份 + PV）。
- 任务强制 Job/CronJob（跑完即止 + 重试）。
- 节点级强制 DaemonSet。

### 自动化/自治闭环

正确的控制器选型是机械自治**正确作用的前提**：**控制器是调谐闭环（第 5 章）的载体，选对控制器，机械自治的自愈/扩缩才符合负载特性**。错配控制器，机械自治会"按错误的方式自愈"（如重建有状态服务丢身份），自愈变破坏。

### 生产检查清单

- [ ] 无状态服务是否用 Deployment？
- [ ] 有状态服务是否用 StatefulSet（稳定身份 + PV）？
- [ ] 节点级服务是否用 DaemonSet？
- [ ] 一次性/定时任务是否用 Job/CronJob？
- [ ] 是否杜绝了"一刀切 Deployment"？

## 7.3 高级调度策略：节点/Pod亲和性、污点容忍、多可用区高可用调度

### 生产问题

某服务 5 个副本全调度到同一个节点/同一可用区，该节点/可用区故障，服务全挂。根因是没配亲和与拓扑分布，默认调度把副本扎堆了。**调度策略缺失，副本分布听天由命，单点/单区故障即全挂**——这是高可用最常见的坑。

### 传统方案失效原因

- **不配亲和/反亲和**：默认调度不保证分散，副本可能扎堆。
- **不用拓扑分布**：靠 podAntiAffinity 表达力弱，跨可用区均匀分布难保证。
- **污点/容忍误用**：专用节点（GPU/控制面）没正确用污点隔离，普通 Pod 抢占专用资源。
- **不考虑故障域**：调度只看资源够不够，不看可用区/节点分散度。

失效根因：**调度只考虑"能不能跑"，不考虑"分散高可用"**。高可用要求副本跨故障域分布，需主动配置调度策略。

### 架构约束与权衡

高级调度策略：

| 策略 | 作用 | 权衡 |
|---|---|---|
| **nodeAffinity** | 钉到特定节点（如 GPU 节点） | 灵活但约束强 |
| **podAntiAffinity** | 副本互斥（不扎堆同一节点/区） | 表达力弱，大规模性能差 |
| **topologySpreadConstraints** | 跨拓扑域均匀分布（推荐） | 精准控制 maxSkew |
| **taint/toleration** | 专用节点隔离（污点排斥，容忍才能调度） | AI/GPU 节点隔离关键 |

权衡的核心：**调度策略用约束换高可用**。约束越多调度越难（资源碎片），但故障域分散越好。生产需平衡分散度与调度可行性。

### 最小可行方案

高可用调度的最小配置：

1. **拓扑分散**：关键服务 `topologySpreadConstraints` 跨可用区 maxSkew=1。
2. **反亲和**：副本不扎堆同节点（podAntiAffinity 或 topologySpread）。
3. **污点隔离**：专用节点（GPU/控制面）打 taint，对应负载配 toleration（第 17 章）。
4. **PDB 配合**：保证自愿中断时最少可用副本（第 5 章）。

### 生产落地实现

- 拓扑分散：`topologySpreadConstraints` 按 `topology.kubernetes.io/zone` 分散。
- 反亲和：`podAntiAffinity` required/preferred，避免同节点扎堆。
- 污点：GPU 节点 `NoSchedule` 污点，仅 AI 负载 toleration（第 17 章）；控制面节点污点隔离（第 4 章）。
- PDB：`minAvailable` 保障，配合滚动更新（第 5 章）。

### 典型故障案例

5 副本扎堆单节点，节点故障全挂。配 `topologySpreadConstraints`（跨 zone/hostname，maxSkew=1）后，副本均匀分散，单节点/单区故障不再全挂。

点评：**topologySpreadConstraints 是多副本高可用的标配**，比 podAntiAffinity 更精准。

### 根因定位

根因不在节点故障，而在**调度策略缺失导致副本扎堆**。高可用要求主动分散故障域，默认调度不保证。

### 长效治理方案

- 关键服务强制拓扑分散（跨可用区 maxSkew=1）。
- 专用节点强制污点隔离（GPU/控制面）。
- PDB 保障自愿中断可用性。
- 调度策略纳入 chart 模板标准化（第 9 章）。

### 自动化/自治闭环

调度策略让机械自治在**故障后依然高可用**：**拓扑分散保证单点/单区故障后剩余副本够用，机械自治（第 5 章）再补足副本**。没有分散，故障直接全挂，机械自治来不及救；有分散，机械自治有时间和余地自愈。调度策略是高可用的第一道防线，机械自治是第二道。

### 生产检查清单

- [ ] 关键服务是否配 topologySpreadConstraints（跨可用区分散）？
- [ ] 副本是否避免扎堆同节点（反亲和/拓扑分散）？
- [ ] 专用节点（GPU/控制面）是否用污点隔离？
- [ ] 是否配 PDB 保障自愿中断可用性？
- [ ] 调度策略是否纳入 chart 模板标准化？

## 7.4 资源配额、层级限制、多租户基础隔离规范

### 生产问题

一个共享集群里，某团队的服务突发吃光节点 CPU/内存，其他团队服务被挤挂（noisy neighbor）；某环境（dev）误操作占满资源，影响 qa/staging。**共享集群无资源隔离，租户/环境之间互相伤害**，"共享省钱"变成"共享互害"。

### 传统方案失效原因

- **无资源 limit**：容器不设 limit，互相挤占。
- **无 namespace 配额**：租户/环境无上限，一个吃光全集群。
- **namespace 当硬隔离**：误以为 namespace 提供资源/故障/安全硬隔离（实际只提供名字隔离）。
- **无默认限制**：新负载不设资源策略，裸奔进集群。

失效根因：**把 namespace 当硬隔离 + 不配资源配额**。namespace 是软边界（第 4 章边界思维），资源隔离需配额 + limit 主动建立。

### 架构约束与权衡

资源隔离三层规范：

| 规范 | 作用 | 权衡 |
|---|---|---|
| **ResourceQuota** | namespace 级总量上限（CPU/内存/Pod 数） | 需按租户/环境规划配额 |
| **LimitRange** | 容器级默认 limit/min/max 兜底 | 防裸奔，但需合理默认 |
| **request/limit** | 每容器资源声明（调度依据 + 上限） | request 影响调度，limit 影响隔离 |

权衡的核心：**资源配额用"上限"换隔离**。配额紧则隔离强但可能调度失败；配额松则易调度但隔离弱。需按租户/环境重要性平衡。

### 最小可行方案

多租户/多环境隔离的最小规范：

1. **每 namespace ResourceQuota**：按租户/环境设总量上限。
2. **LimitRange 兜底**：namespace 内默认 limit，防裸奔容器。
3. **每容器 request/limit**：调度依据 + 单容器上限（第 6 章 cgroup）。
4. **namespace 软边界认知**：明确 namespace 不提供硬隔离，重要隔离上配额/网络策略/分集群。

### 生产落地实现

- ResourceQuota：每个租户/环境 namespace 设 CPU/内存/Pod 总量。
- LimitRange：默认 request/limit，未声明的容器自动套默认。
- request/limit：所有容器声明（request 调度，limit 隔离）。
- 强隔离需求：dev/qa 同集群省钱用配额+网络策略；生产隔离可分集群（附录 A 网络隔离）。

### 典型故障案例

dev 环境一个失控 Pod 吃光节点 CPU，qa 服务受影响。配 ResourceQuota（dev 限额）+ LimitRange（默认 limit）+ 每容器 limit 后，dev 失控被限制在配额内，qa 不再受扰。

点评：**共享集群不配额 = 邀请 noisy neighbor**。配额是多租户共存的底线。

### 根因定位

根因不在某次失控，而在**无资源隔离规范 + namespace 当硬隔离的误解**。软边界不主动加固，必然互害。

### 长效治理方案

- 每个 namespace ResourceQuota + LimitRange。
- 所有容器强制 request/limit。
- 明确 namespace 软边界，强隔离上配额/网络策略/分集群。
- 配额随业务变化定期评审。

### 自动化/自治闭环

资源隔离规范让机械自治的**调度与自愈不影响他人**：**ResourceQuota/limit 保证单租户失控被限制，机械自治（第 5 章）在一个租户内调谐不会挤垮其他租户**。没有隔离，一个租户的扩缩/自愈动作可能挤垮邻居，自治变成新的故障源。隔离是自治安全运行的前提。

### 生产检查清单

- [ ] 每个 namespace 是否配 ResourceQuota（总量上限）？
- [ ] 是否配 LimitRange 兜底（默认 limit）？
- [ ] 所有容器是否声明 request/limit？
- [ ] 是否明确 namespace 是软边界（强隔离上配额/网络策略/分集群）？
- [ ] 配额是否随业务定期评审？

## 7.5 原生HPA生产痛点解析：聚焦K8s原生弹性缺陷，解答「CPU指标正常但业务请求排队、负载异常」核心问题，与第16章KEDA分层解耦

### 生产问题

一个反直觉现象：CPU 利用率稳在 40%（HPA 的扩容线都没碰到），可消息队列越积越深、业务请求排队超时。盯着 dashboard 会一脸懵——**CPU 明明不忙，凭什么说负载过载了？** 这不是 HPA 配错，是它看错了信号：弹性按 CPU 决策，瓶颈却在别处。这是 HPA 最经典的生产痛点——**弹性信号错配**。

### 传统方案失效原因

HPA 的原生缺陷：

- **只懂 CPU/内存**：HPA 默认按 CPU 利用率扩缩，但很多负载的瓶颈不在 CPU（队列消费者瓶颈在队列深度、IO 密集型瓶颈在 IO、推理服务瓶颈在 GPU）。
- **CPU 不忙 ≠ 负载不重**：队列消费者 CPU 不高（在等消息），但队列积压严重；HPA 看 CPU 不扩容，积压恶化。
- **扩缩滞后**：HPA 基于历史指标平滑计算，扩容总是慢半拍，突发流量打穿。
- **缩容震荡**：缩容策略不当导致副本数频繁震荡。

失效根因：**HPA 假设"CPU 利用率反映负载"，但这个假设对大量真实负载不成立**。信号错配，弹性决策必然失准。

### 架构约束与权衡

HPA 痛点与分层解耦策略：

| 痛点 | 原因 | 解耦策略（第 16 章） |
|---|---|---|
| 只懂 CPU | 原生指标源限制 | KEDA 接业务指标（队列深度/请求数/Token 吞吐） |
| 信号错配 | CPU 不反映真实负载 | 按负载真实瓶颈选驱动指标 |
| 扩缩滞后 | 平滑计算 + 历史窗口 | KEDA 预测/快速响应 + 自定义冷却 |
| 适用面窄 | 通用弹性，不懂业务语义 | KEDA 按业务语义弹性（队列/流/推理） |

权衡的核心：**本章只暴露 HPA 的原生缺陷，解法（KEDA）归第 16 章**。这是严格的分层解耦——7.5 讲"为什么 HPA 不够"，16.3 讲"KEDA 怎么补"。不在本章展开 KEDA 实现，保持分层清晰。

### 最小可行方案

针对 HPA 痛点的最小认知与过渡：

1. **识别信号错配**：负载瓶颈不在 CPU 时，HPA 必然失准（这是诊断第一步）。
2. **CPU 密集型用 HPA**：确实 CPU 反映负载的（计算密集），HPA 够用。
3. **非 CPU 瓶颈等第 16 章**：队列/IO/推理瓶颈，用 KEDA 业务指标驱动（不在本章展开）。
4. **调优 HPA 参数**：对适用 HPA 的负载，调 `target CPU`、扩缩稳定窗口，减少震荡。

### 生产落地实现

- 适用 HPA：CPU 密集型服务，HPA + 合理 target/稳定窗口。
- 不适用 HPA：队列消费者/推理服务等非 CPU 瓶颈，本章诊断"HPA 失准"，解法见第 16 章 KEDA。
- 诊断方法：CPU 不高但负载过载（积压/延迟）= 信号错配，需换驱动指标。

### 典型故障案例

开篇的队列消费者：CPU 40% 不扩容但积压严重，根因是 HPA 信号错配（瓶颈在队列深度非 CPU）。诊断确认后，解法是 KEDA 按队列深度驱动（第 16 章），本章只负责识别"HPA 不行"。

点评：**"CPU 正常但排队"是 HPA 失准的标志性现象**，看到它就该想到信号错配，进而到第 16 章找 KEDA。

### 根因定位

根因不在 HPA 配置，而在**HPA 的弹性信号（CPU）与负载真实瓶颈不匹配**。这是 HPA 的原生设计局限，不是调参能解决——必须换驱动指标（第 16 章）。

### 长效治理方案

- 识别哪些负载适合 HPA（CPU 反映负载），哪些不适合。
- 不适合的负载不在 HPA 上死磕，转向第 16 章 KEDA 业务指标弹性。
- 适用 HPA 的负载，调优参数减少震荡/滞后。
- 建立"信号匹配"的弹性选型意识（指标是否反映真实瓶颈）。

### 自动化/自治闭环

本节是 L1 机械自治与 L2 运维自治的**弹性交接点**：**HPA（L1 层的 CPU 弹性）够用时，弹性留在机械自治；HPA 失准时，弹性升级到 L2（KEDA 业务指标驱动，第 16 章）**。识别 HPA 的边界，就是识别"哪些弹性该留在 L1、哪些该上移到 L2"。这个分层解耦，是全书三层自治在弹性领域的具体体现。
