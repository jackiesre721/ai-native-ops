# 全书生产检查清单速查

> 汇总正文各小节「生产检查清单」，按章组织，便于速查。正文未来会精简到每节 2–3 条核心项，完整清单以此文件为准。

## 第1章 云原生与AI原生运维架构演进

**1.1 运维三代范式核心跃迁：被动救火运维 → 云原生自动化运维 → AI原生智能自治运维**

- [ ] 是否还有"必须人盯才能恢复"的工作负载？
- [ ] 变更是否全部声明式 + 版本化（无 SSH 直改生产）？
- [ ] 是否有稳态指标（SLO）在持续度量系统健康度？
- [ ] 高频决策（扩缩/回滚/限流）是否已自动化？
- [ ] 是否已识别哪些负载适合进入第三层（AI 自治）治理？
**1.2 传统分布式运维核心困境与云原生标准化根治思路**

- [ ] 是否还存在"只能在某台机器上跑"的服务？
- [ ] 配置是否有单一真相源（无散落在机器/脚本/人脑的影子配置）？
- [ ] 任意生产环境能否从 Git + 镜像在 30 分钟内重建？
- [ ] 变更是否全部原子化、可回滚？
- [ ] 故障现场是否能精确复现用于复盘？
**1.3 AI原生时代运维重构本质：异构算力、动态模型服务、长任务场景对传统运维体系的颠覆**

- [ ] AI 负载的扩缩是否基于推理语义指标（而非 CPU）？
- [ ] 探针阈值是否考虑了 prefill 阶段的长延迟？
- [ ] 长任务是否有优雅终止和检查点机制？
- [ ] GPU 利用率和显存是否纳入可观测与告警？
- [ ] 滚动更新是否会中断在途推理请求？
**1.4 双原生融合架构核心设计目标：标准化、可观测、可治理、高韧性、可自治**

- [ ] 传统负载与 AI 负载是否共享同一 K8s 底座？
- [ ] 可观测是否一套栈贯通两种负载（含跨负载链路）？
- [ ] 弹性是否按负载特性分层（HPA / KEDA + GPU 感知）？
- [ ] 变更与成本是否有统一治理平面？
- [ ] 故障跨负载传导是否有隔离与快速定位能力？
**1.5 全书核心模型伏笔：现代运维三层自治体系概述（机械自治 → 运维自治 → 智能自治）**

- [ ] L1 是否可靠（所有负载有期望状态且持续调谐）？
- [ ] L2 是否建立（处置决策有 SLO 校验闭环）？
- [ ] 是否避免了"跳级上智能自治"的诱惑？
- [ ] 每一层是否有独立、可信的结果校验机制？
- [ ] 上层决策是否建立在下层可信基础之上？

## 第2章 不可变基础设施与容器软件供应链治理

**2.1 不可变基础设施核心思想与生产约束：杜绝配置漂移、运行时禁改、版本可追溯、故障可复现**

- [ ] 生产镜像是否全部用 digest 锁定（无 `latest`）？
- [ ] 是否还有 SSH 直改生产的操作？
- [ ] 配置是否全部声明式外置（无机器本地影子配置）？
- [ ] 有状态部分是否全部外置（实例可随时销毁重建）？
- [ ] 节点是否有定期重建机制消除漂移？
**2.2 容器生产交付供应链极简链路：镜像构建 → 制品仓库 → 版本追踪 → 漏洞扫描 → 生产发布**

- [ ] 镜像构建是否可复现（同输入同输出）？
- [ ] 是否有统一企业镜像仓库，生产只从此拉取？
- [ ] 镜像 tag 是否规范且 digest 锁定（无 `latest`）？
- [ ] 是否有自动化漏洞扫描且高危阻断发布？
- [ ] 发布是否全部走 GitOps（无 kubectl 直推）？
**2.3 OCI规范、多阶段精简镜像、生产安全构建最小可行实践**

- [ ] 镜像是否多阶段构建（运行镜像无编译工具/源码）？
- [ ] 基础镜像是否精简（distroless/alpine，无 shell）？
- [ ] 基础镜像与依赖是否 digest/版本锁定（构建可复现）？
- [ ] secrets 是否绝不入镜像层（构建期注入）？
- [ ] 镜像是否以非 root 运行？
- [ ] 是否有镜像体积/层数上限的 CI 校验？
**2.4 企业镜像仓库权限、版本管控、安全拦截生产规范**

- [ ] 仓库是否按团队/环境项目隔离 + RBAC 最小权限？
- [ ] production 制品是否开启 tag 不可变 / 删除保护？
- [ ] 生产集群是否只从指定企业仓库拉取（准入校验）？
- [ ] 是否有入库或上线的安全拦截策略（CVE/签名）？
- [ ] 权限矩阵是否定期审计？

## 第3章 AI原生运维统一范式

**3.1 云原生与AI原生运维的边界划分与协同关系**

- [ ] AI 负载与传统负载是否共享同一 K8s 底座？
- [ ] AI 治理层是否只做差异化（不重复底座的共性能力）？
- [ ] AI 治理层是否通过云原生扩展机制接入（无独立控制平面）？
- [ ] 可观测是否一套栈贯通两种负载？
- [ ] 是否避免了对立（两套体系）和混淆（把 AI 当普通服务）两种误判？
**3.2 三类AI负载运维差异：离线训练任务、在线推理服务、智能Agent服务（聚焦运维痛点，不展开AI算法）**

- [ ] 训练任务是否用支持检查点/重试的负载模型，且受中断保护？
- [ ] 推理服务是否用推理信号驱动弹性，且配优雅终止？
- [ ] Agent 服务是否会话状态外置，且配重试限流？
- [ ] 三类负载是否各有标准的工作负载与治理模板？
- [ ] 是否避免了对三类负载一刀切？
**3.3 AI负载专属运维难点：长任务、上下文依赖、不可预测算力、动态KV缓存、推理波动问题**

- [ ] 长任务是否有检查点 + 中断保护 + 优雅终止？
- [ ] 性能与容量是否用百分位（p95/p99）而非平均值？
- [ ] KV 缓存命中率是否纳入监控与告警？
- [ ] TTFT 与 TPOT 是否分开采集与告警？
- [ ] 请求是否按上下文/算力特征分桶治理？
**3.4 AI负载完整生命周期（全书AI章节统一锚点）：训练 → 模型归档 → 模型仓库 → 服务部署 → 在线推理 → 弹性扩缩容 → 可观测治理 → 故障处置 → 成本管控 → 智能自治**

- [ ] 模型交付是否全自动、全版本化、全可追溯？
- [ ] 运维是否覆盖训练/归档/成本等环节（不止部署）？
- [ ] 是否有生命周期级端到端可观测？
- [ ] 模型版本与推理性能是否可回溯关联？
- [ ] 各环节衔接是否由流程驱动（非人工协调）？
**3.5 AI原生运维核心目标：算力可控、推理稳定、成本可控、故障自愈、服务自治**

- [ ] 是否有体系化的五目标，且明确了优先级（稳定 > 成本）？
- [ ] 每个目标是否有可度量指标？
- [ ] 算力是否可控（可调度、可配额、可隔离）？
- [ ] 推理是否有明确的 SLO（延迟/吞吐/可用性）？
- [ ] 降本决策是否受稳定 SLO 的硬约束？
- [ ] 是否已规划从自愈走向自治的路径？

## 第4章 Kubernetes分布式架构与生产治理

**4.1 K8s核心定位：云原生统一操作系统、AI负载统一运行底座**

- [ ] 生产集群为托管形态（ACK Pro / EKS），未自建控制面？
- [ ] 是否所有负载（含 AI）都跑在 K8s 上？
- [ ] 集群版本在云厂商支持矩阵内（4.4）？
- [ ] 节点多可用区分布、规格统一（`kubectl get nodes -L topology.kubernetes.io/zone` 验证过）？
- [ ] K8s 不够用的能力是否通过扩展机制补齐（而非另立底座）？
**4.2 控制平面、节点核心组件架构与高可用生产容错逻辑**

- [ ] 集群托管（ACK Pro / EKS），控制面 SLA 归云厂商？
- [ ] 节点池：多可用区 + 自动修复 + 自动升级 + 维护窗口？
- [ ] Pod 云身份已配 RRSA/IRSA，信任策略 `oidc:sub` 锁到 ns+sa，AK/SK 零进集群？
- [ ] SLB 开删除保护注解，纳入变更管理（防误删）？
- [ ] CSI 存储 / Terway 网络 / 镜像免密拉取逐项过配置？
- [ ] CCM 排障路径（kube-system 日志 + svc Events）团队都知道？
**4.3 调度器、API、控制器架构定位与生产权衡（不展开内部调谐机制，与第5章严格分层）**

- [ ] 团队掌握 API/调度器/控制器职责边界与 Pending 三步定位法？
- [ ] Events 判定表可用（调度问题不靠猜）？
- [ ] 控制面指标（API p99/调度排队/工作队列）有采集与告警？
- [ ] 集群客户端（ArgoCD/监控/CI）LIST 请求都带分页？
- [ ] 容量规划是否基于组件权衡点（而非感觉）？
**4.4 K8s版本生命周期、跨版本滚动升级、兼容性风险治理规范**

- [ ] 集群版本在云厂商支持矩阵内（非 EOL）？
- [ ] 升级节奏每年 ≥2 次小版本（不跨大版本跳级）？
- [ ] 升级前 kubent 弃用扫描 + PDB 覆盖 + 组件兼容矩阵三项预检？
- [ ] 节点分批 ≤20%/批，批间观察 SLO？
- [ ] 升级前完成资源级备份（ACK 备份中心/Velero）？
**4.5 K8s原生架构短板与生产适配边界（进阶架构思维）**

- [ ] 是否摸清 K8s 在弹性/隔离/AI 调度方面的原生边界？
- [ ] 云托管已补的能力（CCM/CSI/Terway）没有重复造轮子？
- [ ] 原生不够处用声明式扩展补齐（而非手工绕过）？
- [ ] 多集群舰队、深度 DR 明确划归 V2？
- [ ] 边界认知随版本/云产品演进定期更新？

## 第5章 声明式API与控制循环核心机制

**5.1 命令式运维与声明式运维的思维本质差异（极简导入）**

- [ ] 运维心智是否从"执行动作"转向"声明状态"？
- [ ] 期望状态是否全部进 Git（无命令式直改生产）？
- [ ] 是否让控制器维持稳态（而非手动维持）？
- [ ] 验证方式是否是"实际状态 == 期望状态"（而非命令执行成功）？
- [ ] 是否杜绝了"应急手改、重建丢失"的循环？
**5.2 核心闭环逻辑：期望状态(Desired) → 调谐循环(Reconciliation) → 实际状态(Actual)**

- [ ] 所有负载是否都纳入控制器（无裸 Pod）？
- [ ] 期望状态是否显式声明且版本化？
- [ ] 实际状态是否持续可观测？
- [ ] 是否信任控制器调谐（而非手动维持）？
- [ ] 调谐频率在大规模下是否经过评估调优？
**5.3 K8s机械自治核心：系统稳态自愈、资源收敛逻辑与生产容错机制**

- [ ] 所有负载是否三探针齐全（liveness/readiness/startup）？
- [ ] 关键服务是否配 PDB 保障最少可用副本？
- [ ] 是否配优雅终止（preStop + 合理 grace period）？
- [ ] 滚动策略（maxUnavailable/maxSurge）是否安全？
- [ ] 闭环本身是否纳入观测（调谐延迟/重启次数/NotReady）？
- [ ] 是否理解最终一致性，容忍短暂偏离并用观测确认收敛？
**5.4 CRD+Operator扩展思想与企业定制化运维落地范式**

- [ ] 复杂生命周期的中间件/服务是否考虑用 Operator 治理（而非外部脚本）？
- [ ] CRD schema 是否合理表达领域期望状态？
- [ ] Operator 调谐逻辑是否覆盖部署/扩缩/备份/恢复？
- [ ] 成熟 Operator 是否沉淀为标准复用？
- [ ] 领域资源是否纳入声明式 + GitOps 管理？
**5.5 增强工作负载：原地升级、Pod打散、Sidecar无感注入生产实践**

- [ ] 大镜像/AI 负载是否用原地升级（避免重建重新加载）？
- [ ] 关键服务是否配拓扑打散（topologySpreadConstraints）+ 反亲和？
- [ ] Sidecar 是否用原生 Sidecar 独立升级（不连累业务）？
- [ ] 有状态服务是否有序滚动 + PV 保持？
- [ ] 增强能力是否按场景选用（非全开）？

## 第6章 Containerd容器运行时生产运维

**6.1 CRI运行时标准演进、Docker淘汰的生产底层逻辑**

- [ ] 集群是否统一采用 containerd（或 CRI-O）作为运行时？
- [ ] 是否已完成 dockershim 迁移（无 Docker 作为运行时）？
- [ ] 构建与运行时是否分离（Docker 构建 / containerd 运行）？
- [ ] 运行时版本是否全集群一致并随 K8s 协同升级？
- [ ] 运行时配置是否纳入版本管理？
**6.2 Containerd、runc核心工作机制、镜像管理、快照、cgroup资源管控**

- [ ] 运行时是否配置镜像 GC（防磁盘爆满）？
- [ ] 快照驱动是否统一（overlayfs）+ 磁盘/inode 监控？
- [ ] 所有容器是否设 cgroup 资源 limit（CPU/内存）？
- [ ] 是否配置镜像仓库 mirror + 并发下载加速？
- [ ] 运行时 `config.toml` 是否纳入版本管理？
**6.3 容器全生命周期运维规范与资源隔离机制**

- [ ] 启动是否用 init 容器处理依赖？
- [ ] 就绪是否用 readiness 探针控制流量接入？
- [ ] 终止是否配 preStop + 合理 grace period（AI/有状态负载加长）？
- [ ] 是否遵循最小权限隔离（非 root/最小 capabilities/禁 hostPath）？
- [ ] 生命周期规范是否按负载特性差异化（短任务 vs AI 长任务）？
**6.4 运行时高频故障：启动异常、镜像损坏、资源卡死、挂载异常闭环排查**

- [ ] 是否建立了四类运行时故障的分类排查路径？
- [ ] 排查是否强制先看 Pod events + 容器/运行时日志？
- [ ] 是否区分了故障层（镜像/网络/存储/运行时）？
- [ ] 故障处理是否沉淀为闭环手册？
- [ ] 高频根因是否反哺为准入校验/告警？

## 第7章 Kubernetes资源与精细化调度治理

**7.1 Pod生命周期、三大探针机制与异常重启、崩溃根因定位**

- [ ] 是否三探针齐全且职责清晰？
- [ ] 慢启动服务是否配 startup 探针？
- [ ] 探针阈值是否基于真实启动时间/延迟（非抄默认）？
- [ ] 崩溃是否按生命周期阶段 + 根因分层排查？
- [ ] OOM 类重启是否定位到内存 limit 调优？
**7.2 核心控制器生产选型：无状态、有状态、守护进程、任务调度适配场景**

- [ ] 无状态服务是否用 Deployment？
- [ ] 有状态服务是否用 StatefulSet（稳定身份 + PV）？
- [ ] 节点级服务是否用 DaemonSet？
- [ ] 一次性/定时任务是否用 Job/CronJob？
- [ ] 是否杜绝了"一刀切 Deployment"？
**7.3 高级调度策略：节点/Pod亲和性、污点容忍、多可用区高可用调度**

- [ ] 关键服务是否配 topologySpreadConstraints（跨可用区分散）？
- [ ] 副本是否避免扎堆同节点（反亲和/拓扑分散）？
- [ ] 专用节点（GPU/控制面）是否用污点隔离？
- [ ] 是否配 PDB 保障自愿中断可用性？
- [ ] 调度策略是否纳入 chart 模板标准化？
**7.4 资源配额、层级限制、多租户基础隔离规范**

- [ ] 每个 namespace 是否配 ResourceQuota（总量上限）？
- [ ] 是否配 LimitRange 兜底（默认 limit）？
- [ ] 所有容器是否声明 request/limit？
- [ ] 是否明确 namespace 是软边界（强隔离上配额/网络策略/分集群）？
- [ ] 配额是否随业务定期评审？
**7.5 原生HPA生产痛点解析：聚焦K8s原生弹性缺陷，解答「CPU指标正常但业务请求排队、负载异常」核心问题，与第16章KEDA分层解耦**

- [ ] 是否识别了哪些负载适合 HPA（CPU 反映负载）、哪些不适合？
- [ ] 出现"CPU 正常但排队"时，是否诊断为 HPA 信号错配（而非死调参）？
- [ ] 非 CPU 瓶颈负载是否规划用 KEDA（第 16 章）替代 HPA？
- [ ] 适用 HPA 的负载是否调优了 target/稳定窗口减少震荡？
- [ ] 是否建立了"弹性信号是否匹配真实瓶颈"的选型意识？

**8.2 Service四层、Ingress七层网关流量管控、路由治理与生产最佳实践**
